## 3. 할 일

1. **Cloud Lab 6장 "관제실: 경보가 울리면"**(이름은 바꿔도 됨). 사건 카드를 같은 순서로 보여 줍니다: 탐지 → 알림 → 판단(런북) → 조치 → 복구 → 기록.
   - 운영 카드 ①: 앱 서버 부족 경보 → Slack ALARM → OK. 실제 장애가 아니라 `set-alarm-state`로 한 **경보 경로 시험**이라고 적습니다. 정확한 시각 기록이 없으니 시각은 쓰지 않습니다. Slack 화면 캡처는 사용자에게 받고, 없으면 문구만 씁니다. 판단 포인트로 "인프라를 올린 직후 거짓 경보를 피하려고 데이터 없음은 판단 보류로 둠"(`alarms.tf` 주석)을 넣으면 좋습니다.
   - 운영 카드 ②: 리전 장애 → Pilot Light. 4장과 겹치므로 숫자 요약(RTO 12분 28초 · 되돌리기 약 6분)과 4장 링크만 둡니다.
   - 보안 카드: 계정 탈취 → 의심 세션의 추가 포인트 사용 보류 → 경보 → 운영자 확인 · 복구. 흐름만 보여 주고 숫자 칸(첫 거래 · 보류 · 경보 시각, 그사이 통과 건수)은 **"실측 대기"**로 둡니다. 구현 · 측정이 끝나면 Claude가 다음 안내문으로 숫자를 넘깁니다.
2. **사건 보고서 1장**(관제 보고서 형식): 리전 DR 2회차로 개요 · 영향(손님은 전환 동안 점검 안내 페이지) · 시각표(선언 → 승격 → 전환 → 복구 → 되돌리기) · 원인(의도한 장애 시험) · 조치 · 개선 후보를 씁니다. 숫자와 단계 시각은 `region-drill.md` 2회차 표와 11-22 안내문 1절에서만 가져옵니다. Cloud Lab에 둘지 포트폴리오에 둘지는 Codex가 판단합니다.
3. **포트폴리오 v2 페이지**에 2절 표를 쉬운 말 3 ~ 5줄로 요약하고 6장 · 보고서로 링크합니다.

## 4. 하지 않을 것

- "24시간 관제 경험", "보안관제 실무"라고 쓰지 않습니다. 교대 관제 근무를 한 적이 없습니다. "관제 흐름(경보 · 판단 · 조치 · 보고)을 직접 만들고 시험함"으로 씁니다.
- 보안은 "보안 전문가"가 아니라 **"MSP가 이관 뒤 맡은 운영 · 보안"**으로 소개합니다(캡스톤 방향, 11-17).
- 시나리오 A의 숫자 · 결과를 구현 · 측정 전에 쓰지 않습니다(설계만 확정, ADR-072).
- Grafana 공개 대시보드의 실시간 화면에만 기대지 않습니다. 실험 날이 아니면 공유를 멈춰 두고, 인프라를 내리면 빈 화면입니다. 기존 performance 페이지처럼 정적 JSON 재생이나 캡처로 보여 줍니다.
- 공고 수 조사 숫자는 사용자 판단용입니다. 포트폴리오에 쓰지 않습니다.
- 원본 로그 · 계정 ID · 이메일을 공개하지 않습니다(기존 원칙).
