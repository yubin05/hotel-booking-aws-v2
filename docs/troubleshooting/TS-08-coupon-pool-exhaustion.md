# TS-08 쿠폰 오픈 순간, 쿠폰과 무관한 숙소 조회까지 0.8초로 느려짐

- 날짜: 2026-11-04 / 관련 실험: [E-03](../07-experiments.md#실험-목록) / 커밋: [e264570](https://github.com/yubin05/hotel-booking-aws-v2/commit/e264570)

## 증상
수량 100장 쿠폰에 1,000명이 같은 순간 발급을 요청하고, 그 앞뒤로 숙소 조회를 초당 100건씩 보냈습니다.
- 쿠폰은 정확히 100장 발급됐습니다(소진 409 900건, 500 0건, 초과 발급 0).
- 그런데 쿠폰과 상관없는 **숙소 조회 p95가 평소 3.9ms → 쏠림 1.26초 동안 813ms(약 210배)**, 최대 848ms로 올랐습니다.
- 쿠폰 요청이 다 끝나자 조회는 바로 3.6ms로 돌아왔습니다.

## 재현
```bash
docker compose down -v && docker compose up -d --build --wait
docker compose exec -T db mysql -uroot -plocal-root-pw hotel_booking -e "UPDATE coupons SET starts_at = UTC_TIMESTAMP() WHERE id = '55555555-0000-0000-0000-000000000003'"
load/run-k6.sh e03-coupon-open.js
node scripts/e03-report.mjs <수정 전>.json.gz <수정 후>.json.gz   # 쏠림 구간 조회 p95, 0.1초 구간별 그래프
```
테스트: `app/test/coupon-review.test.ts`의 "쿠폰 발급이 잠금 앞에 줄 서 있어도 숙소 조회는 바로 응답한다". 다른 연결이 쿠폰 행을 잠근 채 발급 요청 20건을 보내고, 숙소 조회가 2초 안에 응답하는지 봅니다. 수정 전에는 실패합니다.

## 원인 분석
| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 앱 서버나 DB가 바빠서 (CPU) | 100장이 다 나간 뒤 남은 소진 응답이 빠져나간 시간 | 880건이 0.23초 만에 나감. 처리 여유는 있었고, 발급만 한 건당 약 7ms씩 한 줄로 처리됨 → 아님 |
| 잠금을 기다리는 발급 요청이 DB 연결 10개를 모두 쥠 | 조회 지연과 발급 진행을 0.1초 구간으로 비교 | 조회 지연이 발급 줄이 줄어드는 속도에 맞춰 줄고, 줄이 다 빠진 직후 회복 → **맞음** |
| 줄 서기 전 남은 수량 확인(잠금 없는 읽기)이 막아 줄 것 | 소진 응답의 대기 시간 | 같은 순간에 온 요청은 모두 "남음"을 보고 줄을 섬(소진 응답 중앙값 723ms). 늦게 연결된 20건만 3~8ms 만에 거절 |

결론: 발급 트랜잭션은 쿠폰 행 잠금을 기다리는 동안에도 공용 연결을 쥐고 있습니다. 1,000건이 몰리자 연결 10개가 모두 잠금 대기에 묶였고, 뒤에 온 조회는 연결 대기열에서 쿠폰 요청 뒤에 섰습니다(커넥션 풀 고갈 → 장애 전파).

## 해결
- 쿠폰 발급 트랜잭션만 **전용 연결 2개**(`couponPool`)를 쓰게 했습니다. 조회와 다른 기능은 공용 연결 10개를 그대로 씁니다(벌크헤드, 격벽 패턴). [e264570](https://github.com/yubin05/hotel-booking-aws-v2/commit/e264570)
- 2개인 이유: 쿠폰 행 잠금 때문에 발급은 어차피 한 건씩 처리되어 연결을 늘려도 빨라지지 않습니다. 하나가 잠금을 쥐는 동안 다음 하나가 기다리면 잠금이 쉬지 않습니다.
- 줄 서기 전 남은 수량 확인은 공용 연결에 그대로 뒀습니다. 늦게 온 요청을 잠금 없이 바로 돌려보내는 용도라, 전용 연결 뒤에 줄 세우면 그 효과가 사라집니다.
- 고르지 않은 방법
  - 공용 연결 수 늘리기: 1,000건이 늘린 만큼 또 다 차지합니다.
  - 공용 10개 안에서 쿠폰은 최대 2개만 쓰게 세기: 효과는 같지만 직접 만든 세기 코드가 필요합니다. DB 연결 수가 빠듯해지면 다시 검토합니다.
  - RDS Proxy: 트랜잭션이 끝나야 연결을 넘기므로, 잠금을 기다리는 트랜잭션에는 효과가 없습니다.
  - Redis로 수량 관리: 지금 숫자(1,000명에 0.82초)로는 필요 없고 유료입니다.
- 대가: 앱 서버 한 대의 DB 연결이 최대 10개 → 12개가 됩니다. AWS에서는 "태스크 수 × 12"를 RDS `max_connections`와 비교해야 합니다.

## 검증
같은 조건(1,000명, 100장, 조회 초당 100건)으로 수정 전·후 한 번씩 실행했습니다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 발급 / 소진 / 예상 밖 응답 | 100 / 900 / 0 | 100 / 900 / 0 |
| 정합성 검사 (초과 발급 등) | 모두 0 | 모두 0 |
| 평소 조회 p95 | 3.9ms | 3.7ms |
| **쏠림 동안 조회 p95** (중앙값, 최대) | **813ms** (342ms, 848ms) | **133ms** (1.8ms, 224ms) |
| 발급 응답 p95 (최대) | 772ms (951ms) | 913ms (923ms) |
| 100장 소진 | 0.77초 | 0.82초 |

이 문제를 지키는 테스트: `app/test/coupon-review.test.ts` "쿠폰 발급이 잠금 앞에 줄 서 있어도 숙소 조회는 바로 응답한다" (수정 전 실패, 수정 후 통과, CI에서 실행)

## 남은 것
- 요청 1,000건이 **도착하는 첫 0.4초** 동안은 조회가 최대 0.22초 늦습니다. 원인 후보는 두 가지이고 아직 확인하지 않았습니다. ① 줄 서기 전 확인 읽기 1,000건이 공용 연결을 잠깐씩 씀 ② 앱이 요청 1,000건을 한꺼번에 받는 처리. 1초 목표 안이라 보류했습니다.
- 발급 p95가 0.14초 늘었습니다. 소진 응답 900건이 연결 2개로 빠져나가기 때문입니다. "이미 다 떨어짐"을 앱이 기억해 두면 줄일 수 있습니다(후보).
- 발급 요청 일부(1차 20건, 2차 108건)는 연결에만 약 1초가 걸렸습니다(TCP 재전송). 앱 서버의 접속 대기열 한도로 추정하며, 확인하지 않았습니다. AWS에서는 ALB가 접속을 받으므로 3단계에서 다시 봅니다.

## 재발 방지
- 위 테스트가 CI에서 돕니다. 쿠폰 발급이 다시 공용 연결을 쓰게 바뀌면 실패합니다.
- 다음 단계 판단 기준
  - RDS Proxy: AWS에서 "태스크 수 × 12"가 RDS 연결 한도에 가까워질 때. 그 전에 서버당 연결 수 줄이기를 먼저 시도합니다.
  - Redis: 3단계 AWS 재측정에서 쿠폰 발급이 1,000명 기준 1초를 넘을 때. 그 전에 "이미 다 떨어짐" 기억하기를 먼저 시도합니다.

## 면접 한 줄
"쿠폰 오픈 순간 1,000명 동시 요청을 k6로 재현해, 발급 트랜잭션이 행 잠금을 기다리며 DB 연결 10개를 모두 점유하는 바람에 무관한 조회 p95가 3.9ms에서 813ms로 오르는 것을 확인했습니다. 발급 전용 연결 풀로 분리(벌크헤드)해 초과 발급 0을 유지한 채 133ms로 줄였습니다."
