# TS-09 DB가 15초 멈추자 예약 요청이 최대 15.3초 매달림

- 날짜: 2026-11-05 / 관련 실험: [E-04](../experiments/E-04.md) / 커밋: [b14bd57](https://github.com/yubin05/hotel-booking-aws-v2/commit/b14bd57)

## 증상
예약을 초당 10건 보내는 중에 DB를 15초 동안 멈췄습니다. `docker compose pause db`는 MySQL 프로세스만 얼리므로 연결은 열린 채 답만 오지 않습니다.
- 멈춘 동안 들어온 예약 154건 중 105건이 5초 넘게 기다렸습니다. **가장 오래 기다린 예약은 15.3초**(장애 중 p95 14.0초)였고, 기준은 5초입니다.
- 실패는 500 5건뿐이었습니다. 새 연결을 만들려다 정확히 10초 뒤 `connect ETIMEDOUT`(mysql2 연결 제한 시간)으로 끝난 요청입니다. 나머지는 DB가 풀릴 때까지 기다렸다가 성공했습니다.
- DB까지 확인하는 헬스 체크(`/api/health/deep`)는 쿼리에 2초 제한이 있었는데도 최대 13.7초 걸렸습니다.
- 유실 0, 앱 종료 0, 정합성 검사 모두 0이었습니다. 데이터는 안전했고, 사용자를 오래 붙잡은 것이 문제였습니다.

## 재현
```bash
docker compose down -v && docker compose up -d --build --wait
load/e04-db-outage.sh pause   # 부하 시작 15초 뒤 15초 동안 DB 멈춤
node scripts/e04-report.mjs load/results/e04-db-outage-pause-<시각>   # 기준 5개 판정
```
테스트: `app/test/db-timeout.test.ts`의 "DB가 답하지 않으면 연결을 쥔 요청과 빈 연결을 기다리는 요청 모두 3초 안에 503, 멈춘 연결은 다시 쓰지 않는다". 테스트 DB 앞에 둔 중계(TCP 프록시)를 얼려 멈춤을 흉내 냅니다. 시간(sleep)이 아니라 상태로 맞춥니다. 수정 전에는 20초 제한 시간까지 끝나지 않아 실패합니다.

## 원인 분석
| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 연결을 쥔 요청이 멈춘 쿼리의 답을 기다림 | 요청별 시간, 앱 로그 | 연결 10개가 모두 멈춘 쿼리를 쥐고 DB가 풀릴 때까지 기다림 → 맞음 |
| 뒤에 온 요청은 빈 연결을 기다리는 줄에서 끝없이 기다림 | mysql2 풀 코드 | 빈 연결 대기 시간 제한이 없음(`queueLimit`은 줄 길이 제한일 뿐) → 맞음 |
| 쿼리 시간 제한(`timeout`)을 걸면 됨 | 헬스 체크(2초 제한)의 실제 대기, mysql2 `Query._handleTimeoutError` | 제한은 연결을 받은 뒤부터 재서 줄에서 13.7초 기다림. 시간이 지나도 promise만 실패시키고 연결은 닫지 않아, 멈춘 쿼리를 단 연결이 풀로 돌아감 → 아님 |
| 시간이 되면 연결을 `destroy()`하면 됨 | mysql2 `Connection.close()` | 닫는 중이라고 표시한 뒤 소켓만 닫아, 기다리던 쿼리는 실패하지 않음 → 이것만으로는 아님 |

결론: 앱이 DB를 기다리는 시간에 상한이 없었습니다. 연결을 쥔 요청은 멈춘 쿼리를, 나머지는 빈 연결을 DB가 돌아올 때까지 기다렸습니다.

## 해결
- [db.ts](../../app/src/db.ts)에서 **DB 작업 하나(빈 연결 기다리기 + 쿼리)에 3초 상한**을 두었습니다. 넘으면 503 '지금은 처리할 수 없습니다. 잠시 후 다시 시도해주세요.'로 바로 응답하고, 쥐고 있던 연결은 버립니다. 버린 연결은 풀에서 빠지고 더 이상 명령을 보내지 않으므로, 응답한 뒤에 확정(커밋)되는 일을 막습니다. 시간이 지난 뒤에 받은 연결은 쓰지 않고 돌려줍니다. [b14bd57](https://github.com/yubin05/hotel-booking-aws-v2/commit/b14bd57)
- `pool.query`와 `withTransaction`에 모두 적용해, DB를 부르는 25곳 넘는 코드는 그대로 뒀습니다. 헬스 체크의 2초 쿼리 제한은 위 이유로 빼고 같은 상한을 씁니다.
- 3초인 이유: 평소 DB 작업은 수십 ms이고, 쿠폰 오픈 쏠림(E-03)에서 가장 오래 기다린 발급도 1.3초입니다. 사용자 기준 5초 안에 답하면서 정상 요청은 끊지 않는 값입니다.
- 500이 아니라 503인 이유: DB가 잠시 안 되는 상황이라 "잠시 후 다시 시도"가 맞는 안내입니다.
- 고르지 않은 방법
  - 모든 쿼리에 mysql2 `timeout`: 줄에서 기다리는 시간은 못 막고, 멈춘 연결이 풀로 돌아갑니다.
  - 연결 제한 시간(`connectTimeout`)만 줄이기: 이미 만들어진 연결에서 멈춘 쿼리에는 효과가 없습니다.
  - 요청 단위로 응답만 먼저 보내기(응답 시간 초과 미들웨어): 뒤에서 작업이 계속되어, 503을 받은 예약이 DB가 풀린 뒤 확정될 수 있습니다.
  - TCP keepalive: 프로세스만 멈춘 DB도 운영체제는 응답하므로 끊김을 알아채지 못합니다.
- 대가: 멈춘 동안 기다리면 성공했을 요청이 3초 만에 실패합니다(500 5건 → 503 123건). 이미 보낸 COMMIT은 막지 못하므로, 멈추는 순간의 예약은 "응답은 실패인데 DB에 생김"이 될 수 있습니다(3회 모두 0건). 이런 예약은 같은 멱등키로 다시 시도하면 처음 예약을 돌려받습니다(E-05에서 확인).

## 검증
같은 조건(예약 초당 10건, 부하 시작 15초 뒤 15초 멈춤)으로 수정 전 1회, 수정 후 3회 실행했습니다(2026-11-05).

| 항목 | 수정 전 | 수정 후 (3회 범위) |
|---|---|---|
| **가장 오래 기다린 예약** | **15.3초** | **3.0초** |
| 장애 중 기다린 시간 p95 | 14.0초 | 3.0초 |
| 실패 | 500 5건 | 503 123건 (3회 모두) |
| 쓰기 불가 구간 | 15.4초 | 15.3~15.4초 |
| 풀린 뒤 첫 예약 성공 | 36ms | 25~35ms |
| 유실 / 응답은 실패인데 DB에 생긴 예약 / 앱 종료 | 0 / 0 / 0 | 0 / 0 / 0 |
| 정합성 검사 | 모두 0 | 모두 0 |

수정이 다른 실험을 깨지 않는지도 확인했습니다. E-04 ① 재시작은 수정 후 3회 모두 기준을 통과했고 3초 상한에 걸린 요청은 0건이었습니다. E-03 쿠폰 쏠림 1회도 예상 밖 응답 0, 정확히 100장이었습니다(가장 오래 기다린 발급 1.09초).

이 문제를 지키는 테스트: `app/test/db-timeout.test.ts` (수정 전 실패, 수정 후 통과, CI에서 실행)

## 남은 것
- 상한은 DB 작업 하나 기준입니다. 쿠폰 발급처럼 DB 작업을 두 번 하는 요청은 DB가 멈추면 최대 약 6초까지 기다릴 수 있습니다. 요청 단위 상한이 필요해지면 바꿉니다.
- 시간 초과 503은 앱 로그에 남지 않습니다(앱이 정한 오류라 에러 처리기가 기록하지 않음). 2단계 모니터링에서 ALB 5xx 지표로 보거나 로그를 추가합니다.
- 실제 장애(RDS 장애 조치)는 접속 주소(DNS)가 새 서버로 바뀌고 시간이 더 깁니다 → 4단계에서 쓰기 불가 시간을 잽니다.

## 재발 방지
- 위 테스트가 CI에서 돕니다. 시간 상한이 빠지면 20초 제한 시간에 걸려 실패합니다.
- `load/e04-db-outage.sh`와 `scripts/e04-report.mjs`로 같은 조건을 다시 잴 수 있습니다(기준 자동 판정).
