# 07. 로컬 장애·부하 실험

실사용에서 터질 만한 상황을 로컬(docker compose)에서 일부러 만들고, 무엇이 깨지는지 숫자로 확인합니다.
비용은 0원입니다. 같은 k6 스크립트를 1·3·4단계(AWS)에서도 그대로 씁니다.

**로컬과 AWS의 역할 나누기**: 로컬에서는 앱 버그(교착, 중복, 멱등키, 종료 처리, DB 재연결)를 찾아 고칩니다.
AWS에서는 로컬에서 재현할 수 없는 것만 잽니다. 성능 숫자, RDS 장애 조치, 대체 태스크 기동, 오토스케일링이 여기에 해당합니다.
AWS 실험이 끝날 때도 [정합성 검사](#정합성-검사)는 돌립니다. 쿼리 한 번이라 비용이 거의 들지 않습니다.
로컬에서 재현되지 않는 위험은 [아래 목록](#로컬에서-안-보이는-위험)에 따로 적어 AWS 단계에서 확인합니다.

## 진행 방식

1. 아래 목록에서 실험 하나를 고릅니다 (번호 순서대로 추천).
2. 실행 **전에** 기대 결과를 적습니다. 예측과 실측의 차이가 기록의 핵심입니다.
3. 실행하고 측정값을 적습니다.
4. 실험이 끝나면 [정합성 검사](#정합성-검사)를 돌립니다.
5. 결과에 따라 이렇게 기록합니다.
   - 기대대로면 아래 표의 "결과" 칸에 날짜와 숫자만 적고 끝냅니다.
   - 기대와 다르면 [트러블슈팅](troubleshooting/README.md)에 TS-08부터 한 건씩 기록합니다.

## 실험별 메모 (어디가 깨질 것 같은지)

**E-01 기준선**
- 측정: 에러율 1%를 넘는 지점의 처리량(초당 요청 수), p95 응답 시간.
- 의심: 앱의 DB 연결이 10개뿐이고([db.ts](../app/src/db.ts)) 대기 줄에 제한이 없습니다. 그래서 몰려도 에러 대신 응답 시간만 늘어날 수 있습니다. 에러율만으로는 한계를 못 잡을 수 있으니 p95 기준(예: 1초)도 함께 봅니다.
- 로컬 숫자는 PC 성능에 좌우되므로 AWS 숫자와 직접 비교하지 않습니다. 로컬에서는 무엇이 먼저 느려지는지와 데이터가 깨지지 않는지를 봅니다.
- 1판 검토 (2026-11-05): 데이터 정합성 검사는 맞게 설계됐지만(409 27건도 같은 조건 모의 2,000회 평균 32건과 비슷해 정당한 거절로 봄), "평소 성능" 근거로는 허점이 있었습니다.
  1. 요청 구성이 화면과 다름: 홈(추천 숙소·도시·쿠폰), 리뷰, 내 쿠폰·내 예약, 로그인이 빠짐. 빠진 것 중 추천 숙소는 방문마다 모든 숙소를 묶어 계산하고, 로그인(scrypt)은 CPU를 가장 많이 씀
  2. 예약이 너무 많음: 한 사람이 평균 30초마다 예약 시도(70초에 815건, 하루로 치면 약 100만 건)
  3. 데이터가 너무 적음: 숙소 10개·객실 30개라 표 전체를 훑는 검색(`city LIKE %서울%`)과 추천 숙소 쿼리도 공짜처럼 빠름
  4. 합격 기준이 실패율 하나뿐: 응답이 5초여도 통과
- 2판 변경: 방문 하나를 화면 흐름대로 보냄(화면 하나가 동시에 부르는 API는 `http.batch`로 한꺼번에). 방문의 10%는 로그인, 3%는 예약(1~90일 뒤, 1~3박), 5%는 내 예약 확인. 화면 사이 5~20초. 요청 종류별 p95 합격 기준 추가. 데이터는 [seed-volume.sql](../scripts/seed-volume.sql)로 숙소 1,000 / 객실 5,000 / 회원 2만 / 지난 예약 10만 / 리뷰 5만. 방문 하나가 약 1분이라 유지 구간을 30초 → 90초로 늘림
- 측정하지 않는 것: 숙소 이미지와 웹 화면 파일(HTML·JS·CSS). 이미지는 외부(Unsplash) URL이라 브라우저가 우리 서버를 거치지 않고 직접 받고, 남의 서버에 부하를 거는 것도 안 됩니다. 웹 화면 파일은 AWS에서 CloudFront가 캐시해 앱까지 오지 않습니다. 이미지까지 포함한 "화면이 뜨는 체감 속도"는 부하와 별개로 브라우저 1대로 잽니다(Lighthouse)
- 실행 전 예측 (2026-11-05, 2판): ① 서버 에러 0건 ② 초당 요청은 화면 하나가 API 2~3개를 부르므로 쉬는 시간이 같다면 1판(약 140건/초)의 2~3배 (실제 쉬는 시간은 평균 6.5초 → 12.5초로 약 2배) ③ 가장 느린 요청은 예약(DB에 쓰기 때문) ④ 추천 숙소(홈 첫 화면)는 사용자가 지연을 못 느낄 만큼, 0.1초 이하 ⑤ 로그인 p95는 길어도 1초 ⑥ 예약 수는 예측 없음 (계산상 방문 약 1,000번 × 3% ≈ 25~30건) ⑦ 요청 종류별 p95 기준을 모두 지킴 (지켜야 평소라고 할 수 있음)
- 2판 1차 실행 (2026-11-05 11:21, `e01-normal-traffic-20261105-112142`): 합격 기준 모두 통과. 서버 에러 0 (요청 11,761건이 모두 200·201), 응답 확인 10,404건 100% 통과. 500명 유지 구간(30~120초)은 초당 86.6건(1판 약 137건의 0.63배). 유지 구간 p95는 로그인 180ms > 추천 숙소 26ms > 검색 21ms > 예약 19ms > 나머지(숙소·리뷰·도시·쿠폰·내 예약) 4~6ms. 10초 구간별 전체 p95는 사용자 50명대(0~10초) 23ms, 500명 유지 내내 17~22ms로 사람 수가 늘어도 그대로. 방문 1,085번, 예약 28건(409 0건). 방문 210번은 끝날 때 사용자 수를 줄이며 중간에 멈춤(실패 아님). 정합성 검사 모두 0, k6 예약 28건 = DB 28건. 그래프·표: `node scripts/e01-report.mjs <실행>.json.gz`
- 예측과 비교: ① 맞음 ② 늘지 않고 줄어듦. 1판도 한 번 쉴 때마다 요청 1.8개(검색+상세 또는 예약)를 보냈으므로 화면당 2.2개는 1.2배뿐이고, 쉬는 시간이 2배라 약 0.6배 ③ 가장 느린 건 예약이 아니라 로그인(비밀번호 해시를 일부러 느리게 계산). 그다음이 숙소 1,000개를 훑는 추천 숙소·검색이고, 예약은 객실·날짜 몇 줄만 읽고 써서 빠름. 느린 원인은 "쓰기"가 아니라 "한 번에 훑는 데이터 양" ④ 26ms로 0.1초 안 ⑤ 180ms로 1초 안 ⑥ 28건 (계산 25~30건) ⑦ 모두 통과

**E-02 인기 객실 동시 예약**
- 0단계 테스트는 동시 10건이었고, 여기서는 수를 늘리고 날짜가 엇갈리는 예약(1~3일, 2~4일 …)을 섞습니다.
- 스크립트: [e02-popular-room.js](../load/e02-popular-room.js). 시드 첫 숙소의 스탠다드 룸 하나에 200명(계정 200개)이 같은 순간 한 번씩 예약합니다. 100명은 모두 60일 뒤 2박이고, 나머지 100명은 70일 뒤부터 하루씩 밀린 2박 10가지(10명씩)라 이웃 날짜끼리 하루씩 겹칩니다. 엇갈린 쪽 성공 수는 도착 순서에 따라 4~5건입니다.
- 측정: 응답 코드 분포, 교착 발생 수. `SHOW ENGINE INNODB STATUS`는 마지막 교착 1건만 보여 주므로 개수는 `SELECT COUNT FROM information_schema.INNODB_METRICS WHERE NAME='lock_deadlocks'`로 셉니다(MySQL 8.4에서 기본으로 켜져 있고, DB를 새로 띄우면 0부터 셈).
- 의심: MySQL에서 같은 키를 기다리던 INSERT들은 앞 트랜잭션이 취소되면 서로 교착할 수 있습니다. 그러면 409 대신 500이 나갑니다.
- 실행 전 예측 (2026-11-04): 같은 날짜는 1건만 성공하고 99건은 거절, 엇갈린 날짜는 날짜마다 예약이 0건 또는 1건, 겹치는 요청은 모두 409, 500 0건, 교착은 0건일 것 같지만 생길 수도 있음(확신 없음).
- 1차 실행 (2026-11-04 17:38): 201 5건(같은 날짜 1건, 엇갈린 날짜 4건), 정상 거절 409 195건, 예상 밖 응답 0건(500 0). 200건이 0.3초 안에 모두 끝남(예약 한 건 최대 0.28초). 교착 0건(`lock_deadlocks` 0). 정합성 검사 모두 0, k6 예약 5건 = DB 5건. 엇갈린 쪽 확정 예약은 1/13~15, 1/16~18, 1/19~21, 1/22~24이고, 남은 빈 밤(15·18·21일)은 모두 하룻밤씩 떨어져 있어 2박 요청이 들어갈 자리가 없음 (거절 195건이 모두 정당)
- 예측과 비교: 모두 예측대로. 다만 교착은 앞 예약이 취소되는 순간 그 날짜를 기다리던 요청이 둘 이상 있어야 생기는 타이밍 문제입니다. 이번 1회 실행에서 0건이었다고 일어날 수 없다는 증명은 아닙니다. 지금 코드에서는 교착이 나면 500으로 나갑니다

**E-03 쿠폰 오픈 쏠림**
- 시드의 '주말 특가 10,000원 할인'(100장)을 지금 열어 두고, 가입을 마친 1,000명이 같은 순간에 한 번씩 요청합니다. 시작 시각에 시계를 맞출 필요가 없고 '아직 시작 전'(400) 응답도 섞이지 않습니다. 조회는 쏠림 10초 전부터 20초 뒤까지 초당 100건씩 보냅니다(응답이 느려져도 보내는 양은 그대로).
- 준비: DB를 새로 띄우고 쿠폰을 엽니다.
  ```bash
  docker compose down -v && docker compose up -d --build --wait
  docker compose exec -T db mysql -uroot -plocal-root-pw hotel_booking -e "UPDATE coupons SET starts_at = UTC_TIMESTAMP() WHERE id = '55555555-0000-0000-0000-000000000003'"
  ```
- 측정: 발급 수, 응답 코드 분포, 발급 요청의 p95·최대 응답 시간, 초당 발급 수(쿠폰 한 행의 처리 상한), **같은 시간 조회 p95**.
- 의심: 모든 발급 요청이 쿠폰 한 행의 잠금을 기다리며 줄을 섭니다. 그동안 DB 연결 10개를 다 차지하면 쿠폰과 무관한 조회까지 느려집니다(장애 전파).
- 실행 전 예측 (2026-11-04): 정확히 100장, 남았는데 거절 0, 500 0건, 발급 응답은 아무리 늦어도 1초 이내, 100장은 1초 안에 다 나감, 조회 p95는 그 순간 늘어난 요청 배수(약 11배)만큼 느려짐.
- 1차 실행 (수정 전, 2026-11-04 15:18): 201 100건·소진 409 900건·예상 밖 0건, 정합성 검사 모두 0. 100장이 0.77초 만에 다 나감(초당 약 130장). 발급 p95 772ms·최대 951ms. 소진 응답도 중앙값 723ms를 기다림(줄 서기 전 남은 수량 확인이 같은 순간에 온 요청에는 효과 없음). 연결 20건(2%)은 TCP 재전송으로 약 1초 늦게 연결됐고 3~8ms 만에 소진 응답. **조회 p95가 평소 3.9ms → 쏠림 1.26초 동안 813ms(약 210배)**, 쏠림이 끝나자 3.6ms로 회복. 원인: 잠금을 기다리는 발급 요청이 DB 연결 10개를 모두 쥠 → 쿠폰 발급 전용 연결 2개로 분리([TS-08](troubleshooting/TS-08-coupon-pool-exhaustion.md))
- 수정 후 예측 (2026-11-04): 쏠림 순간 조회 p95 1초, 발급 p95 1초, 100장 소진 1초.
- 2차 실행 (수정 후, 2026-11-04 15:53): 201 100건·소진 409 900건·예상 밖 0건, 정합성 검사 모두 0. **조회 p95 평소 3.7ms → 쏠림 1.34초 동안 133ms(중앙값 1.8ms, 최대 224ms)**. 늦어진 조회는 요청 1,000건이 도착하는 첫 0.4초에만 있고, 잠금을 기다리는 나머지 구간은 평소 수준(0.1초 구간별 p95 1~7ms). 발급 p95 913ms(수정 전 772ms), 100장 소진 0.82초(0.77초): 소진 응답이 연결 2개로 빠져나가며 0.1초쯤 늦어짐. 연결이 약 1초 늦은 요청은 108건(1차 20건).
- 예측과 비교: 조회는 1초 예측보다 훨씬 좋음(0.13초), 발급 p95(0.91초)와 100장 소진(0.82초)은 1초 예측과 비슷. 수정 전 조회는 11배 예측보다 훨씬 나빴음(약 210배).
- 분석: `node scripts/e03-report.mjs <수정 전>.json.gz <수정 후>.json.gz` (표 숫자와 포트폴리오 그래프)

**E-04 예약 중 DB 재시작**
- 측정: 쓰기 불가 구간(첫 실패부터 마지막 실패까지), 실패 수, 사용자가 받은 상태 코드와 메시지, `/api/health/deep`이 회복된 시각.
- 의심 (하나씩 확인합니다):
  1. 끊긴 연결이 풀에 남아 DB가 돌아온 뒤에도 한동안 에러가 납니다.
  2. 연결 오류가 처리되지 않아 앱 프로세스가 죽습니다.
  3. 사용자에게 500과 내부 오류 메시지가 그대로 보입니다.
  4. DB가 내려간 동안 요청이 연결을 기다리며 오래 매달립니다.
- ②의 `pause`를 쓰는 이유: `restart`는 DB가 연결을 정상적으로 닫아서 앱이 바로 오류를 받습니다. 실제 장애는 DB가 아무 응답 없이 사라질 수 있습니다. `pause`는 연결을 열어 둔 채 응답만 멈추므로 이 상황에 더 가깝습니다.

**E-05 앱 강제 종료 후 재시도**
- k6가 실패한 요청을 같은 `Idempotency-Key`로 다시 보냅니다. 멱등키는 예약과 같은 트랜잭션에 저장됩니다.
- 측정: 중단 구간, 실패 수, 재시도 결과(201/200/409) 분포, 키당 예약 수.
- 로컬 compose에는 재시작 정책이 없어 수동으로 다시 띄웁니다(ECS는 대체 태스크를 자동으로 띄움). 그래서 로컬에서는 중단 시간보다 **중복·유실**에 집중합니다.

**E-06 배포 중 정상 종료**
- 시간 재기: `time docker compose stop app`. Docker는 SIGTERM을 보내고 10초 안에 안 끝나면 강제 종료합니다.
- 의심: 부하 도구가 연결을 유지한 채(keep-alive) 계속 요청을 보내면 [server.ts](../app/src/server.ts)의 `server.close`가 끝나지 않습니다. 그러면 10초를 다 채우고 강제 종료되며, 처리 중이던 요청이 끊깁니다. ECS의 기본 대기 시간은 30초라서 배포 때마다 30초씩 늦어질 수 있습니다.

## 로컬에서 안 보이는 위험

로컬에서 통과해도 AWS에서 깨질 수 있는 것들입니다. 해당 단계에서 확인하고, 문제가 나오면 트러블슈팅으로 기록합니다.

| 위험 | 로컬에서 안 보이는 이유 | 확인 시점 |
|---|---|---|
| 가끔 502 에러 | Node는 쉬는 연결을 5초 뒤 닫는데([server.ts](../app/src/server.ts)에 별도 설정 없음) ALB는 60초까지 재사용하려 합니다. 이미 닫힌 연결로 요청을 보내면 502가 납니다. 로컬에는 ALB가 없습니다 | 2단계 배포 직후 E-01 부하에서 502 개수 |
| DB 연결 수 초과 | 태스크마다 연결 10개라서 태스크가 늘면 RDS 최대 연결 수를 넘을 수 있습니다. 로컬은 앱이 1개입니다 | 2단계 설계 때 계산, 3단계 오토스케일링 중 확인 |
| DB 장애 조치 때 요청이 오래 매달림 | 실제 장애는 연결 종료 신호 없이 사라질 수 있습니다. E-04 ②로 일부만 흉내 낼 수 있습니다 | 4단계 RDS 장애 조치 |
| 작은 Fargate CPU에서 로그인 몰림 | 비밀번호 해시(scrypt)는 1번에 메모리 약 32MiB를 쓰고 CPU를 많이 씁니다. 쿠폰 오픈 직전 로그인이 몰리면 응답이 느려지고 헬스체크가 실패해 태스크가 교체될 수 있습니다. 로컬 PC는 CPU가 넉넉합니다 | 3단계 쿠폰 스파이크에 로그인 포함 |
| DB 설정 차이 | RDS 파라미터 그룹의 기본값(잠금 대기 시간, 문자셋 등)이 컨테이너 MySQL과 다를 수 있습니다 | 2단계에서 `SHOW VARIABLES` 비교 |
| 앱과 DB 사이 지연 | 다른 AZ에 있으면 쿼리마다 지연이 생겨 잠금을 쥐는 시간이 길어집니다. 그만큼 쿠폰 행 처리량이 줄어듭니다 | 3단계 E-03 재측정 |

## 공통 준비

- **k6**: `grafana/k6` Docker 이미지라서 설치할 것이 없습니다. compose 네트워크에 붙여 `http://app:3000`으로 요청합니다. 이미지는 `grafana/k6:1.0.0`으로 고정했습니다.
- **스크립트 위치**: `load/`에 실험마다 `eNN-이름.js` 파일 하나를 둡니다. 기본은 [e01-normal-traffic.js](../load/e01-normal-traffic.js)이고, 나머지 실험은 이를 복사해 고쳐 씁니다.
- **실행**: `load/run-k6.sh e01-normal-traffic.js` (실행기 하나로 모든 실험을 돌립니다). 터미널 출력은 `load/results/<이름>-<시각>.txt`, 그래프 리포트는 같은 이름의 `.html`, 요청 하나하나의 기록은 `.json.gz`로 저장됩니다(git에서 제외).
- **사용자·토큰**: 회원가입은 k6 준비 단계(`setup`)에서만 합니다(비밀번호 해시라 느림). 로그인은 E-01에서 방문 일부가 실제로 합니다.
- **깨끗한 상태에서 시작**: `docker compose down -v && docker compose up -d --build --wait`
- **데이터 양 채우기** (E-01부터, 약 10초): `docker compose exec -T db mysql -uroot -plocal-root-pw --default-character-set=utf8mb4 hotel_booking < scripts/seed-volume.sql`. 시드만으로는 숙소가 10개라 성능 숫자를 믿을 수 없습니다. E-02·E-03(2026-11-04)은 시드만으로 실행했습니다. E-02는 객실 하나에 몰리는 실험이라 영향이 거의 없고, E-03의 조회 p95는 데이터가 늘면 달라질 수 있습니다
- **Git Bash 주의**: `docker run -v`의 경로가 Windows 경로로 바뀌면 `MSYS_NO_PATHCONV=1`을 앞에 붙입니다.
