## 기록

- 하는 일: 예약을 초당 10건(60초), DB까지 확인하는 헬스 체크(`/api/health/deep`)를 초당 1건 보냅니다. 부하 시작 15초 뒤 장애를 넣습니다. 손으로 넣으면 시각·길이가 매번 달라지므로 시각과 길이는 스크립트가 정합니다.
  - ① 재시작: `load/e04-db-outage.sh restart` (`docker compose restart -t 3 db`). 종료 신호를 보내고 3초 안에 끝나지 않으면 강제 종료(SIGKILL)한 뒤 다시 띄웁니다. 첫 시도(`-t` 없음)에서 부하 중인 MySQL이 3초 안에 정상 종료를 끝내지 못해 강제 종료됐습니다. 그래서 확정 예약이 강제 종료에도 남는지까지 보게 되고, 같은 조건이 되도록 3초를 적어 둡니다. 다시 뜨는 시간은 MySQL이 정합니다.
  - ② 멈춤: `load/e04-db-outage.sh pause` (`docker compose pause db` → 15초 뒤 `unpause`). 15초는 앱 쪽 시간 제한(헬스 체크 쿼리 2초, mysql2 새 연결 10초)보다 길게 잡은 값입니다.
- 준비: 실행마다 DB를 새로 띄웁니다(시드만). `docker compose down -v && docker compose up -d --build --wait`
- 반복: ①·② 각각 같은 조건 3회, 결과는 범위로 적습니다.
- 기준 (실행 전에 정함, 분석 스크립트가 판정):

  | 기준 | 숫자 | 이유 |
  |---|---|---|
  | 앱 재시작 없이 회복 (의심 2) | 앱 컨테이너 종료 0회 | compose에 재시작 정책이 없어 앱이 죽으면 그대로 멈춰 있습니다 |
  | 끊긴 연결이 남지 않음 (의심 1) | DB가 준비되고 2초가 지난 뒤 시작한 예약의 실패 0건 | 2초는 로그 기록 시각과 실제 연결을 받는 시각 사이의 여유입니다 |
  | 확정 예약 유실 0 | 201을 받은 예약 키가 DB에 모두 있음 (키 단위 대조) | 개수만 비교하면 유실 1건과 '응답은 실패인데 DB에 생긴 예약' 1건이 서로 가려집니다 |
  | 내부 오류 노출 없음 (의심 3) | 5xx 응답은 앱이 정한 문구('서버 오류가 발생했습니다.', TS-09 뒤로는 시간 초과 503 '지금은 처리할 수 없습니다. 잠시 후 다시 시도해주세요.')만, 응답 없음(상태 0) 0건 | 장애 중 실패(500) 자체는 허용합니다. 오류 코드·SQL·호스트 이름이 보이면 실패입니다 |
  | 오래 매달리지 않음 (의심 4) | 사용자가 기다린 시간(연결 + 응답) 최대 5초 | 예약 p95 기준(1초)의 5배입니다. 성공이든 실패든 답을 받아야 사용자가 다시 누를지 정할 수 있습니다 |
  | 정합성 검사 | 모두 0 | 공통 |
- 측정: DB 중단 구간(Docker 기록), 쓰기 불가 구간(201 응답이 끊긴 가장 긴 구간), 상태 코드·메시지별 개수, 장애 전·중·회복 뒤 사용자가 기다린 시간 p95, DB 준비 → 첫 예약 성공·헬스 체크 200까지 걸린 시간, 응답은 실패인데 DB에 생긴 예약 수(→ E-05).
- 시각 맞추기: 장애 시각은 Docker가 기록한 사건(`kill`·`pause`·`unpause`)과 MySQL 로그의 'ready for connections'에서 꺼냅니다. k6도 Docker 안에서 돌기 때문에 시계가 같습니다(Windows 시계와는 어긋날 수 있음).
- 분석: `node scripts/e04-report.mjs load/results/<이름>`. 요청 수가 k6 반복 수와 다르면 멈춥니다.
- 로컬 한계 (실행 전에 적어 둠):
  - `restart`는 DB가 연결을 정상적으로 닫고 같은 이름·주소로 돌아옵니다. RDS 장애 조치는 대기 DB로 넘어가고 접속 주소(DNS)가 새 서버를 가리켜야 해서 순서와 시간이 다릅니다 → 4단계.
  - `pause`는 MySQL 프로세스만 얼립니다. 운영체제는 연결 요청을 계속 받아 주므로 TCP 연결은 되고 MySQL의 첫 응답만 오지 않습니다. 네트워크에서 아예 사라진 DB(패킷이 사라짐)와는 다르지만, 앱 입장에서는 둘 다 '답이 없음'이라 매달림 확인에는 충분합니다.
  - 부하 시작 15초 뒤, 멈춤 15초는 임의로 정한 값입니다. 실제 장애 길이와 다릅니다.
  - k6·앱·DB가 같은 PC입니다. 이번 실험은 속도가 아니라 동작(회복·유실·매달림)을 보므로 영향이 작습니다.
  - 앱이 1대입니다. 여러 대면 대마다 연결 풀이 따로 회복합니다 → 3·4단계.
- 고칠 때: 문제를 지키는 회귀 테스트는 시간(sleep)이 아니라 상태로 맞춥니다. 예를 들어 테스트용 중계(TCP 프록시)를 DB 앞에 두고, '연결을 받았다'는 신호가 온 뒤 멈춤을 흉내 냅니다.
- 의심 (하나씩 확인합니다):
  1. 끊긴 연결이 풀에 남아 DB가 돌아온 뒤에도 한동안 에러가 납니다.
  2. 연결 오류가 처리되지 않아 앱 프로세스가 죽습니다.
  3. 사용자에게 500과 내부 오류 메시지가 그대로 보입니다.
  4. DB가 내려간 동안 요청이 연결을 기다리며 오래 매달립니다.
- ②의 `pause`를 쓰는 이유: `restart`는 DB가 연결을 정상적으로 닫아서 앱이 바로 오류를 받습니다. 실제 장애는 DB가 아무 응답 없이 사라질 수 있습니다. `pause`는 연결을 열어 둔 채 응답만 멈추므로 이 상황에 더 가깝습니다.

- 원인과 수정 (TS-09): mysql2에는 빈 연결을 기다리는 시간 제한이 없고, 쿼리 `timeout`은 promise만 실패시킬 뿐 연결을 닫지 않습니다(멈춘 연결이 풀로 돌아가 다음 요청도 그 뒤에 줄을 섬). `destroy()`도 기다리던 쿼리를 실패시키지 않습니다. 그래서 [db.ts](../../app/src/db.ts)에서 DB 작업 하나(빈 연결 기다리기 + 쿼리)에 3초 상한을 두고, 넘으면 503 '지금은 처리할 수 없습니다. 잠시 후 다시 시도해주세요.'로 응답하며 쥐고 있던 연결은 버리게 했습니다. `pool.query`와 `withTransaction` 모두 적용되어 호출하는 곳은 그대로입니다. 3초는 평소 DB 작업(수십 ms)과 E-03 쿠폰 쏠림에서 가장 오래 기다린 발급(1.3초)보다 길게 잡은 값입니다. 회귀 테스트([db-timeout.test.ts](../../app/test/db-timeout.test.ts))는 테스트 DB 앞에 둔 중계를 얼려 멈춤을 흉내 냅니다. 수정 전 코드에서는 20초 제한 시간까지 끝나지 않아 실패하고, 수정 후에는 3.06초에 통과합니다. 전체 테스트 28개도 통과합니다.
