# 1.5단계 DB 병목 분석과 개선

[← 03 진행 계획](../03-plan.md) · 결정: [ADR-024](../04-decisions.md#adr-024) · 출발점: [1단계 기준선](baseline.md)

1단계에서 옛날 구조는 동시 접속 500명에서 DB가 먼저 한계(CPU 91~93%)였다. 3단계로 가기 전에 로컬(비용 0)에서 원인을 찾아 앱을 고치고, 고친 앱으로 같은 옛날 구조를 다시 잰다. 1단계 기록은 그대로 둔다.

## 한눈에 보기

1단계 옛날 구조는 동시 접속 500명에서 DB가 먼저 꽉 찼다. 원인과 함께 "꽉 찬 뒤 어떻게 무너지는지"를 나눠 고쳤다.

| 문제 | 쉬운 말 | 원인 | 고친 방법 | 결과 (로컬) |
|---|---|---|---|---|
| ① 왜 일찍 꽉 찼나 (병목) | 요리사가 손님마다 메뉴판 전체 가격을 새로 계산하고 8개만 보여 줌 | 추천 숙소가 매번 숙소 1,000개 · 객실 5,000개의 최저가를 다 계산한 뒤 평점순 8개만 남김 → DB 시간의 약 60% | 평점순 8개를 먼저 고르고 그 8개만 계산 (일이 약 1/100) | DB 0.3코어에서 1,000명 에러 90% → **0%**, p95 318ms |
| ② 꽉 찬 뒤 어떻게 무너지나 | 손님이 떠나도 주방은 그 요리를 계속 만듦(우주 쓰레기) + 계속 새로 전화 연결 | 앱이 3초가 지나면 DB 연결을 끊는데, DB는 끊긴 조회를 계속 실행(실행 중인 조회 14 > 앱 연결 10). 앱은 새 연결을 수천 번 다시 맺음 | 조회(SELECT) 시간 상한 2초를 MySQL이 직접 지키게 함 → DB가 스스로 끝내고 연결은 그대로 다시 씀 | DB 0.1코어 과부하에서 500명 에러 57% → 39%, 동시 실행 조회 최대 10 → 6. **연결 재접속은 그대로**(아래 남은 일) |
| ③ 실패라고 했는데 실제로는 성공 | ATM이 "오류"라고 했는데 송금은 됨 | 예약 확정(COMMIT)은 DB에서 끝났는데 그 답이 오기 전에 앱의 3초가 지나 503. 시간 초과는 실패가 아니라 "결과를 모름" | 예약 화면이 503 · 연결 실패면 같은 멱등키로 1초 · 2초 뒤 자동 재시도 → 이미 저장됐으면 그 예약을 돌려받음 | 화면 테스트 4개로 확인 (k6는 화면이 아니라 확인 대상 아님) |

## 2. 조회별 DB 시간 (2026-11-11, 로컬, 300명 2분, CPU 제한 없음)

MySQL `performance_schema.events_statements_summary_by_digest`로 2분 동안 조회 종류별 DB 시간을 모았다. 요청 7,232건, 실패 0.

| 조회 | 호출 | 평균 | 1회에 읽는 행 | DB 시간 |
|---|---|---|---|---|
| **추천 숙소 (홈, `/api/hotels/featured`)** | 806 | 13.6ms | **6,048** | **11.0초 (약 60%)** |
| 검색 결과 (`/api/hotels?city=…`) | 805 | 3.1ms | 1,665 | 2.5초 |
| 검색 결과 개수 (같은 조건으로 COUNT) | 805 | 3.0ms | 108 | 2.4초 |
| 도시 목록 (`/api/hotels/cities`) | 1,612 | 0.6ms | 1,019 | 0.9초 |
| 나머지 (숙소 상세 · 객실 · 리뷰 · 가입 · 예약) | | 0.1~7.5ms | 0~60 | 합 1.5초 이하 |

**추천 숙소가 비싼 이유 (실행 계획 `EXPLAIN ANALYZE`로 확인):** 화면에 보여 주는 건 평점순 8개인데, 조회는 숙소 1,010개 전부에 객실 5,030개를 붙여 숙소마다 최저가를 계산한 다음 정렬해서 8개만 남긴다. 버리는 1,002개의 최저가까지 매번 계산한다. 결과는 모든 손님에게 똑같다.

```
Limit: 8 → Sort(평점) → Group aggregate(최저가) rows=1010 → Nested loop left join rows=5030
  → Index scan on hotels(PRIMARY) rows=1010 → rooms(fk_rooms_hotel) 숙소마다 약 5개
```

고칠 방향: 평점순 8개를 먼저 고르고 그 8개의 객실만 붙인다.

## 3. 로컬 재현 (DB 컨테이너 CPU 0.3코어, 500명 4분 → 1,000명 4분)

PC의 DB는 t3.micro보다 빨라서 CPU를 0.3코어로 묶어 DB가 먼저 꽉 차게 했다. 숫자가 아니라 모양을 본다. 10초마다 DB 처리 목록(`information_schema.PROCESSLIST`)과 CPU를 남겼다.

- 500명부터 DB가 제한(30%)에 붙어 있고, 실행 중인 조회는 거의 다 추천 숙소였다.
- **실패로 받았는데 저장된 예약이 재현됨**: k6 성공 32건, DB 35건(3건). 1단계 2회차(1건)와 같은 현상.
- **앱 연결 수(10)보다 많은 조회가 DB에서 실행됨**(최대 13), DB 연결 번호가 8분 동안 약 7,700 늘어남. 앱이 3초가 지나면 연결을 끊고 새로 맺기를 반복했고, 끊긴 연결의 조회 일부가 DB에서 계속 돌았다는 뜻(가설 1을 뒷받침). MySQL 매뉴얼에는 연결이 끊겼을 때 실행 중인 조회를 어떻게 하는지 적혀 있지 않아 관찰로만 확인했다.
- 1단계 AWS에서 본 "DB가 한가한데 실패 99%"는 로컬에서는 나오지 않았다(로컬 DB는 끝까지 제한에 붙어 있음). AWS 재측정 때 다시 본다.

## 4-1. 추천 숙소 수정

[hotel/index.ts](../../app/src/hotel/index.ts): 평점순 8개를 먼저 고르고, 최저가는 고른 8개에 대해서만 하위 조회로 계산한다. 같은 점수면 id순으로 고정했다. 테스트: 예전 조회(전체를 묶어 계산)와 결과(숙소 · 최저가 · 순서)가 같은지 확인([booking.test.ts](../../app/test/booking.test.ts)).

실행 계획: 최저가 계산이 숙소 8개에만 돈다(`loops=8`, 객실 약 40행). 조회 시간 14.4ms → 0.98ms(같은 데이터, 부하 없음).

| 같은 조건(DB 0.3코어) | 고치기 전 | 고친 뒤 |
|---|---|---|
| 500명 | 에러 0.01%, p95 3.2초 → 무너짐 | 에러 0%, p95 10ms → 버팀 |
| 1,000명 | 에러 90.2% → 무너짐 | 에러 0%, p95 318ms → 버팀 |
| 처리량 (1,000명) | 초당 154건(대부분 실패) | 초당 174건(모두 성공) |
| 추천 숙소의 DB 시간 (8분) | 2,670초 (평균 562ms) | 27.7초 (평균 4ms) |
| 실패로 받았는데 저장된 예약 | 3건 | 0건 (179 = 179) |

이제 DB 시간을 가장 많이 쓰는 건 검색 결과(105초)와 그 개수 세기(102초)다. 같은 조건을 두 번 실행하는 구조라 줄일 여지가 있지만, 1,000명에서 p95 318ms로 기준 안이라 후속 후보로 둔다.

## 4-2. 무너지는 방식: 조회 시간 상한을 MySQL이 직접 지키게

[db.ts](../../app/src/db.ts): 새 연결마다 `SET SESSION max_execution_time = 2000`을 건다. MySQL은 2초가 넘은 SELECT를 스스로 끝내고(`ERROR 3024 … maximum statement execution time exceeded`, 로컬 MySQL 8.4에서 직접 확인), 앱은 이 오류를 연결을 버리지 않고 503으로 바꾼다. 쓰기와 DB가 아예 답하지 않는 경우는 기존 3초 상한(TS-09)이 그대로 막는다.

- 근거: [MAX_EXECUTION_TIME](https://dev.mysql.com/doc/refman/8.4/en/optimizer-hints.html)(읽기 전용 SELECT에 적용, 시간이 지나면 서버가 끝냄). mysql2 3.24.6 소스에서 promise 풀이 새 연결 이벤트를 연결을 넘겨주기 직전에 내는 것을 확인해 그 자리에서 설정한다.
- 테스트([db-timeout.test.ts](../../app/test/db-timeout.test.ts)): 새 연결에 상한이 걸려 있고, 오래 걸리는 조회는 ERROR 3024로 끝나며 같은 연결을 그대로 다시 쓰고, 앱 경로에서는 503이 된다. 앱 테스트 29개 통과(화면 빌드 후, CI와 같은 순서).

| DB 0.1코어 과부하 (추천 숙소 수정 후) | 수정 전 | 수정 후 |
|---|---|---|
| 500명 에러율 | 56.9% | 38.9% |
| 1,000명 에러율 | 86.4% | 85.3% |
| 성공한 요청 | 13,994건 | 17,353건 (+24%) |
| DB에서 동시에 실행 중이던 조회 최대 | 10 | 6 |
| 새로 맺은 연결 (약 9분) | 약 7,600 | 약 10,800 |
| 실패 응답 시간 중앙값 | 3.0초 | 3.0초 |

연결 재접속이 줄지 않은 이유: 실패의 대부분이 여전히 "연결을 3초 기다리다 포기"다. 대기 줄에서 1초 넘게 기다린 요청은 MySQL의 2초 상한보다 앱의 3초 타이머가 먼저 울려 연결을 끊는다.

## 4-3. 시간 초과된 예약: 화면이 같은 멱등키로 자동 재시도

[api.ts](../../app/web/src/api.ts) `withRetry`, [BookingPage.tsx](../../app/web/src/pages/BookingPage.tsx): 예약 요청이 502 · 503 · 504 또는 연결 실패면 1초 · 2초 쉬고 같은 멱등키로 다시 보낸다. 409(이미 예약된 날짜) 같은 확실한 거절은 다시 보내지 않는다. 테스트 4개([api.test.ts](../../app/web/src/api.test.ts)), 화면 테스트 12개 · 빌드 통과.

- 재현: 로컬 과부하에서도 "k6 성공 수 < DB 저장 수"가 반복됨(0.3코어 32 vs 35, 0.1코어 0 vs 1, 1 vs 4). k6 시나리오는 화면을 거치지 않고 재시도하지 않으므로(1 · 3단계 비교용으로 고정) 이 차이는 계속 남고, 화면에서는 재시도로 해결된다.

## 남은 일 (후속 후보)

- **연결 재접속 줄이기**: 3초가 지나도 연결을 바로 끊지 말고 DB가 끝낼 때까지 잠깐 기다렸다 돌려주거나, 대기 줄이 너무 길면 기다리게 하지 말고 바로 거절(`queueLimit`, mysql2 소스에서 동작 확인). DB 장애 보호(TS-09)를 건드리는 변경이라 따로 설계한다.
- **검색 조회**: 이제 DB 시간이 가장 많은 조회. 같은 조건을 목록과 개수로 두 번 실행한다.
- **추천 숙소 캐시**: 결과가 모든 손님에게 같아 몇 초 재사용할 수 있다(3단계 CloudFront 자리 포함).
- **AWS 옛날 구조에서 고친 앱으로 재측정** (약 $0.3, 사용자 확인 후): "같은 구조, 앱만 고쳐서 N명". 1단계에서만 보인 "DB · 앱이 한가한데 실패 99%"도 이때 본다. [run-baseline.sh](../../infra/legacy/run-baseline.sh)가 30초마다 앱 입구(연결 대기 줄 · 연결 추적 표)와 DB 처리 목록을 자동으로 남긴다(`app.snap` · `db.snap`, 지켜볼 필요 없음).
- 참고: 이전 환경 DB 서버는 apply할 때 GitHub main의 schema.sql을 받는다. 이번에는 스키마를 바꾸지 않았지만, 바꾸면 옛날 구조 재현에도 섞이므로 그때는 커밋을 고정한다.
