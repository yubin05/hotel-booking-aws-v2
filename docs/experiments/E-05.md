## 기록

- 하는 일: `load/e05-app-kill.sh`. 예약을 초당 10건(60초), 헬스 체크를 초당 1건 보냅니다(E-04와 같음). 부하 시작 15초 뒤 앱을 강제 종료(`docker compose kill -s SIGKILL app`)하고 5초 뒤 다시 띄웁니다(`docker compose start app`). compose에 재시작 정책이 없어 다시 띄우는 것도 스크립트가 합니다(ECS는 대체 태스크를 자동으로 띄움). 시각·길이는 스크립트가 정합니다.
- 다시 누르기: 응답이 없거나(상태 0: 연결 거부·끊김) 5xx면 1초 뒤 같은 `Idempotency-Key`·같은 본문으로 다시 보냅니다. 최대 20번. 본문을 같게 두는 이유: 앱은 같은 키면 본문이 달라도 처음 예약을 돌려줍니다(알려진 shortcut).
- 중복을 막는 장치: 멱등키는 예약과 같은 트랜잭션에 저장되고 `UNIQUE (user_id, idempotency_key)`가 같은 키의 두 번째 예약을 막습니다. 같은 키가 다시 오면 앱은 200 '이미 처리된 요청입니다.'와 처음 예약을 돌려줍니다.
- 준비: 실행마다 DB를 새로 띄웁니다(시드만, E-04와 같음). 반복: 같은 조건 3회, 결과는 범위로 적습니다.
- 기준 (실행 전에 정함, 분석 스크립트가 판정):

  | 기준 | 숫자 | 이유 |
  |---|---|---|
  | 중복 0 | DB에서 키 하나당 예약 1건 이하 | 이 실험의 목표 |
  | 받은 예약 = DB 예약 | 201·200으로 끝난 키마다 사용자가 받은 예약 번호가 DB의 그 키 예약 번호와 같음 (없으면 유실) | 200이 엉뚱한 예약을 돌려주거나 확정 예약이 사라지면 개수 비교로는 안 보입니다 |
  | 모르는 예약 0 | 다시 보낸 뒤에도 실패로 끝났는데 DB에 있는 예약 0건 | 사용자는 실패로 알고 있는데 확정된 예약입니다 |
  | 모든 키가 답을 받음 | 20번 안에 201·200·409로 끝나지 않은 키 0개 | 앱이 다시 뜨면 다시 누른 예약은 결국 처리되어야 합니다 |
  | 내부 오류 노출 없음 | 5xx는 앱이 정한 문구만. 상태 0(응답 없음)은 앱이 죽은 동안이라 허용 | E-04와 같음 |
  | 앱 종료 | 넣은 강제 종료 1회만 | 다시 띄운 앱이 또 죽지 않음 |
  | 정합성 검사 | 모두 0 | 공통 |
- 측정 (기준 아님, 예측과 비교): 앱 중단 구간(강제 종료 → 다시 띄운 앱이 'listening on'을 찍은 때, Docker 기록), 처리 불가 구간(201·200이 끊긴 가장 긴 구간), 첫 시도 상태 분포, 종료 순간 처리 중이던 시도, 다시 보낸 키 수와 마지막 답(201/200/409) 분포, 가장 많이 다시 보낸 횟수, 다시 보낸 키가 답을 받기까지 걸린 시간, 시도 하나에서 기다린 시간, 앱이 받기 시작 → 첫 예약 답.
  - 200으로 끝난 키는 앞 시도가 저장됐는데 응답이 끊긴 예약(E-04의 '응답은 실패인데 DB에 생긴 예약')이 다시 보내서 풀린 경우입니다.
- 시간 재기: 시도 하나의 기다린 시간은 k6 스크립트가 직접 잽니다(보낸 순간 → 답). k6 타이밍(blocked + duration)은 연결이 실패하면 모두 0으로 남아 보낸 시각과 기다린 시간을 잃습니다(스모크 점검에서 확인).
- 분석: `node scripts/e05-report.mjs load/results/<이름>`. 키 수가 k6 반복 수와 다르거나 키마다 시도 번호가 1부터 빠짐없이 있지 않으면 멈춥니다.
- 로컬 한계 (실행 전에 적어 둠):
  - 강제 종료 순간 처리 중인 예약은 드뭅니다. 예약 하나가 수십 ms라 초당 10건이면 그 순간 처리 중인 요청은 평균 1건이 안 되고, '저장은 됐는데 응답 전'인 틈은 그보다 훨씬 짧습니다. 그래서 200으로 끝나는 키는 0건일 가능성이 큽니다. 같은 키를 다시 보내면 처음 예약을 돌려주는 동작은 테스트([booking.test.ts](../../app/test/booking.test.ts) '같은 멱등키로 다시 보내면 새로 만들지 않고 처음 예약을 돌려준다')가 따로 확인합니다.
  - 앱이 죽은 동안 k6는 Docker 내부 DNS에서 `app`을 찾지 못하거나 사라진 주소로 연결하려다 몇 초 기다린 뒤 실패합니다(스모크 점검에서 최대 7.2초, 앱이 다시 뜬 뒤 1~2초까지 이어짐). 앱이 아니라 로컬 네트워크 동작이라 기준에서 빼고 측정만 합니다. AWS에서는 사용자가 ALB에 붙고, 살아 있는 대상이 없으면 ALB가 답합니다 → 4단계.
  - Docker는 같은 컨테이너를 다시 시작합니다. ECS는 새 태스크를 띄우고 ALB 헬스 체크를 통과해야 요청을 받습니다 → 4단계 '대체 태스크 기동 시간'.
  - 5초 중단, 1초 간격으로 다시 누르기, 최대 20번은 임의로 정한 값입니다. 실제 사용자는 더 늦게 다시 누르거나 포기합니다.
  - k6(Go의 HTTP 클라이언트)는 `Idempotency-Key` 헤더가 있는 요청을 재사용하던 연결이 끊겼을 때 한 번 스스로 다시 보낼 수 있습니다. 이런 재전송은 시도 수에 잡히지 않습니다.
  - k6·앱·DB가 같은 PC이고 앱이 1대입니다(E-04와 같음).
- 고칠 때: 회귀 테스트는 시간(sleep)이 아니라 상태로 맞춥니다(E-04와 같음).
- 실제 화면도 같은 키로 다시 보냅니다: [BookingPage.tsx](../../app/web/src/pages/BookingPage.tsx)는 입력(객실·날짜·인원·쿠폰)이 같으면 같은 멱등키를 써서, 버튼을 여러 번 눌러도 이 실험의 재시도와 같습니다. 화면은 스스로 다시 보내지 않고 사용자가 누를 때만 보냅니다.

  - 중복이 없는 이유: 앱이 죽어 있는 동안 보낸 예약은 저장되지 않았고, 다시 보낸 시도가 처음 접수가 되어 201을 받았습니다. 처리 중에 끊긴 1건도 트랜잭션이 커밋되기 전이라 되돌려졌고, 다시 보낸 시도가 같은 키로 1건만 만들었습니다. 이미 저장된 키가 다시 왔다면 `UNIQUE (user_id, idempotency_key)`가 막고 200을 돌려줍니다(3회에서는 이 경우가 나오지 않아 테스트로 확인).
  - 처리 불가 구간이 앱 중단보다 1~2초 긴 이유: 앱이 다시 받기 시작한 뒤에도 k6가 앱이 없을 때 시작한 DNS 조회를 기다리다 함께 실패했습니다(앱이 받기 시작한 뒤 보낸 시도 18건). 앱 쪽 문제가 아니라 로컬 DNS 동작으로 보고, 자세한 원인은 확인하지 않았습니다.
  - 409 1~3건은 다시 보내는 동안 다른 사람이 그 날짜를 먼저 예약한 경우입니다. 첫 시도의 409 비율(약 2%)과 비슷하고, 이 키들은 DB에 예약이 없습니다(모르는 예약 0).

  3. 첫 시도 실패 0에 가깝게 → 틀림(80~81건). 서버 1대로는 막을 수 없고, 서버 여러 대 + ALB가 필요합니다 → 4단계.
  4. 대부분 200 → 틀림(200 0건, 201 78~79건). 앱이 죽은 뒤 보낸 요청은 저장되지 않아서, 다시 보낸 요청이 처음 접수입니다. 예약이 1건뿐이라는 목표는 맞았습니다.
  5. 다시 누르기 적게 → 최대 3번. 다시 누르는 간격이 1초로 고정이라 횟수는 중단 시간에 따라 정해집니다. 실제 화면은 사용자가 누를 때만 보냅니다.
  6. 답까지 0.5초 → 다시 누른 마지막 시도 자체는 빠르지만(앱이 있을 때 p95 약 150ms), 처음 누른 때부터는 8.7~9.2초였습니다.
  7. 중복 0 · 모르는 예약 0 · 내부 오류 노출 없음 → 맞음. "다시 누르기 1번 안에 답" → 틀림(최대 3번).
