## 조건과 한계 (실행 전에 적음)

- **HTTP.** 3단계는 HTTPS(CloudFront)라 암호화 연결 비용이 더해진다. 1단계 HTTP에서 예약 화면이 멈춘 사례처럼 조건 차이가 동작을 바꿀 수 있다([03 결과 기록](../03-plan.md#결과-기록)).
- **가입 계정 50개를 손님들이 나눠 씀.** 3,000개를 만들면 가입(느린 비밀번호 해시)에 몇 분이 걸려 시험 전에 앱 CPU를 쓰고, 계정 목록이 손님마다 복사돼 발생기 메모리가 커진다. 회원이 많은 DB는 seed-volume의 회원 2만 명으로 갖춤(로그인은 안 되는 회원).
- **발생기 1대 = 출발지 IP 1개.** 실제 사용자는 IP가 많다. 3단계 WAF 요청 수 제한은 IP 기준이라 같은 방식이면 발생기가 차단될 수 있다 → 3단계 설계 때 확인.
- **인터넷 지연 없음.** 같은 서울 리전이라 발생기 → 앱 4.4ms(내 PC → 앱 14.4ms, 각 1회). 측정값은 서버가 일한 시간에 가깝다.
- **t3 크레딧 unlimited.** 크레딧 제한 없이 잰다(IDC 서버 · Fargate와 같은 조건).
- **회차 사이 DB · 앱은 그대로.** 예약이 회차마다 수백 건 쌓이지만 지난 예약 10만 건에 비하면 작다.
- **숙소 이미지 · 화면 파일(HTML · JS)은 요청하지 않음**(E-01과 같음).
- **발생기가 병목이면 그 회차는 무효.** 발생기 CPU 80% 이상 또는 메모리 90% 이상(k6 권장선).

### 관찰

- **DB가 먼저 한계.** 500명 층에서 DB CPU 평균 93%(최대 100%), 동시에 실행 중인 작업 수(vmstat `r`) 7~11 = 앱의 DB 연결 10개가 모두 쉬지 않고 일함. 앱 CPU는 18~21%. 그래서 500명에서 p95가 이미 0.76~0.96초로 기준(1초)에 붙어 있었다. 한계는 500~1,000명 사이(계단이 500명 단위).
- **발생기는 병목이 아님(두 회차 모두 유효).** 발생기 CPU 최대 41%, 여유 메모리 2.1GB 이상.
- **실패 종류(1회차 분당 집계).** 대부분 503(앱이 DB 연결을 3초 넘게 기다리다 포기)이고, 일부는 앱에 연결 자체를 못 함(`dial: i/o timeout`, 3,000명 층에서 분당 약 1,600건). 예상 못 한 오류(500)는 0건이라 앱 로그에도 오류가 없다(503은 로그를 남기지 않음). 앱·DB 재시작, 메모리 부족 종료 없음.
- **이상한 점(원인 미확인).** 1,000명 층부터 DB CPU는 99%와 0~30%를 오가다 1,500명부터 평균 0~3%, 앱도 9~13%로 오히려 한가한데 실패가 97~99%다. 바빠서가 아니라 어딘가 막힌 상태. 부하가 끝나자 앱은 바로 정상(상태 확인 200, 17~45ms).
  - 가설 1: 3초가 지나 앱이 끊은 연결의 조회를 MySQL이 끝까지 실행해, 아무도 기다리지 않는 조회가 DB 시간을 쓴다(그런데 DB가 한가한 구간과는 맞지 않음).
  - 가설 2: 앱 서버가 새 연결을 받지 못하는 한계(연결 대기열·연결 추적 표)에 걸린다.
  - 3회차 1,000명 층(8~11분)에서 DB 처리 목록(`SHOW FULL PROCESSLIST`)을 찍어 확인한다. 2회차에는 실시간으로 볼 사람이 없어 찍지 못함.
- **실패로 받았는데 저장된 예약 1건(2회차).** k6 성공 92건, DB 93건(1회차는 97 = 97). 사용자는 실패 화면을 봤는데 예약은 됐다. [db.ts](../../app/src/db.ts) 주석의 "이미 보낸 COMMIT은 막지 못한다"(확정 명령을 보낸 직후 3초가 지나 503) 경우로 보이며 확인 필요. 실제 사용자라면 같은 멱등키로 다시 누르면 기존 예약을 돌려받는다.
- **t3 steal.** 크레딧 unlimited인데 앱·DB·발생기 모두 vmstat `st`(가상화 층이 CPU를 가져간 비율)가 순간 최대 9~20%. 같은 물리 서버 이웃의 영향으로 보이나 확인하지 않음.
- 2회차 중 PC의 실시간 로그 보기(SSH)가 끊김(무너진 뒤 경고가 초당 수백 줄). 시험은 발생기에서 끝까지 돌았고 `collect`로 회수. 화면에서는 경고를 거르도록 [run-baseline.sh](../../infra/legacy/run-baseline.sh) 수정.

### 3회차에서 할 것

순서는 [이전 환경 README](../../infra/legacy/README.md#부하-기준선-시험-날-과제-3) 그대로(다른 PC면 `git pull` · SSH 허용 IP 수정 · 새로 apply). 시작하고 **8~11분 사이(진행 줄 `1000/3000 VUs`)** 다른 Git Bash 창에서(먼저 `eval "$(ssh-agent -s)"; ssh-add ~/.ssh/hotel-legacy`):

```bash
cd /c/dev/hotel-booking-aws-v2/infra/legacy
APP=$(terraform output -raw web_instance_1_public_ip); DB=$(terraform output -raw db_instance_1_private_ip)
ssh -J ec2-user@$APP ec2-user@$DB "sudo docker exec hotel-db sh -c 'mysql -uapp -p\"\$MYSQL_PASSWORD\" -e \"SHOW FULL PROCESSLIST\"' 2>/dev/null | head -40" > ~/processlist-1000.txt
ssh ec2-user@$APP 'ss -s; ss -ltn "sport = :80"; sudo dmesg -T | grep -i conntrack | tail -3' > ~/app-sockets-1000.txt
```

DB에서 실행 중인 조회가 10개보다 훨씬 많고 `Time`이 3초를 넘으면 가설 1, 앱의 80번 대기열(`Recv-Q`)이 꽉 찼거나 conntrack 경고가 있으면 가설 2 쪽이다. 두 파일을 결과 폴더와 함께 Drive에 둔다.
