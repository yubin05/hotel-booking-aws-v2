## 기록

- 보는 것: 새 버전 배포 때 옛 서버가 문을 닫는 법. 가게로 치면 "새 손님은 그만 받고, 계산 중인 손님은 마저 계산해 드린 뒤 문 닫기"입니다(정상 종료, graceful shutdown). [server.ts](https://github.com/yubin05/hotel-booking-aws-v2/blob/d04aad9257eb038e2eb3446131102b9de7aadf5e/app/src/server.ts)는 정상 종료 신호(SIGTERM)를 받으면 `server.close`로 새 연결을 그만 받고, 연결이 모두 끝나면 DB 연결을 닫고 종료 코드 0으로 끝납니다. 정해진 시간 안에 끝나지 않으면 Docker·ECS가 강제 종료(SIGKILL, E-05)합니다.
- 하는 일: `load/e06-graceful-stop.sh`. 부하는 E-05와 같습니다(같은 [e05-app-kill.js](https://github.com/yubin05/hotel-booking-aws-v2/blob/39d08196c7ef0c4bc7ff2370bba035cc3c5e7acd/load/e05-app-kill.js): 예약 초당 10건 60초, 헬스 체크 초당 1건). 부하 시작 15초 뒤 DB를 멈추고(`docker compose pause db`), 1초 뒤 앱에 정상 종료 신호를 보내고(`docker compose stop -t 10 app`), 다시 1초 뒤 DB를 풉니다. 앱이 끝나면 스크립트가 바로 다시 띄웁니다(`docker compose start app`, 새 버전 시작 흉내). 시각·길이는 스크립트가 정합니다.
  - 강제 종료까지 기다리는 시간 10초를 `-t 10`으로 적습니다(compose 문서에 기본값이 적혀 있지 않고, E-04 교훈대로 기본값에 기대지 않음). ECS `stopTimeout` 기본은 30초입니다.
  - DB를 2초 멈추는 이유: 예약 하나가 수십 ms라 종료 신호 순간 처리 중인 예약이 보통 0~1건입니다(E-05 3회 0·0·1건). 0건이면 "처리 중 요청은 응답하고 종료"를 판정할 수 없어서, 멈춘 동안 들어온 예약 약 10건을 DB 답을 기다리는 '처리 중'으로 붙잡아 둡니다(느린 결제처럼 오래 걸리는 요청 역할). 2초는 앱의 DB 작업 상한 3초([TS-09](../troubleshooting/TS-09-db-hang-timeout.md))보다 짧아 503이 나지 않습니다(스모크 점검에서 확인).
- 다시 누르기: E-05와 같습니다. 응답이 없거나(상태 0) 5xx면 1초 뒤 같은 `Idempotency-Key`·같은 본문으로 다시 보냅니다. 최대 20번. 서버 입장에서는 사람이 다시 누르든 화면이 자동으로 다시 보내든 같은 키로 한 번 더 온 요청이라 둘 다 이것으로 봅니다.
- 준비: 실행마다 DB를 새로 띄웁니다(시드만, E-05와 같음). 반복: 같은 조건 3회, 결과는 범위로 적습니다.
- 기준 (실행 전에 정함, 분석 스크립트가 판정):

  | 기준 | 숫자 | 이유 |
  |---|---|---|
  | 정상 종료 | 종료 코드 0, 강제 종료 신호(SIGKILL) 없음 = 10초 안에 스스로 끝남 (Docker 사건 기록) | 강제 종료(137)면 그 순간 처리 중이던 요청이 끊깁니다 |
  | 처리 중이던 예약은 모두 답 | 종료 신호 순간 처리 중이던 시도가 모두 201·200·409. 1건 이상 있어야 판정 | 이 실험의 목표 ("계산 중인 손님은 마저 계산") |
  | 앱에 닿은 뒤 끊긴 요청 0 | 응답 없음(상태 0) 중 연결 거부(`dial:`)·주소 못 찾음(`lookup:`)이 아닌 것 0건 (연결 끊김 `read: connection reset` 등) | 닿지도 못한 요청은 다시 누르면 되지만, 닿은 뒤 끊기면 처리됐는지 모릅니다 |
  | 중복 0 · 받은 예약 = DB · 모르는 예약 0 · 모든 키가 답을 받음 | E-05와 같음 | 다시 누르기가 안전한지 |
  | 내부 오류 노출 없음 | 5xx는 앱이 정한 문구만 | E-04와 같음 |
  | 앱 종료 | 넣은 정상 종료 1회만, DB 종료 0회 | 다시 띄운 앱이 또 죽지 않음 |
  | 정합성 검사 | 모두 0 | 공통 |
- 측정 (기준 아님, 예측과 비교): 종료 신호 → 앱 종료 시간(그중 DB 풀기 → 종료, 옛 버전의 마지막 답 → 종료), 예약 못 받는 시간(종료 신호 → 새 버전이 받기 시작), 처리 불가 구간(201·200이 끊긴 가장 긴 구간), 종료 신호 순간 처리 중이던 시도 수와 기다린 시간, 종료 신호 뒤 보낸 시도와 옛 버전이 답한 수, 다시 누르기로 늘어난 요청 수, 다시 보낸 키 수·마지막 답·최대 횟수, 다시 보낸 키가 답을 받기까지 걸린 시간, 평소(DB 멈춤 전) 시도 하나의 기다린 시간, 새 버전 받기 시작 → 첫 예약 답.
- 시간 재기: 시도 하나의 기다린 시간은 k6 스크립트가 직접 잽니다(E-05와 같음). 종료 신호·종료 코드·DB 멈춤·풀기는 Docker 사건 기록(`signal`, `exitCode`)으로 봅니다. `time docker compose stop`은 쓰지 않습니다(Windows 시계라 k6 기록과 맞출 수 없음).
- 분석: `node scripts/e06-report.mjs load/results/<이름>`. E-05처럼 키 수 = k6 반복 수, 키마다 시도 번호 1..n을 확인하고, DB 멈춤 → 종료 신호 → DB 풀기 순서가 아니면 멈춥니다.
- 의심 (공식 문서 확인 뒤 고침, 2026-11-05):
  - 처음 의심은 "부하 도구가 연결을 유지(keep-alive)하면 `server.close`가 끝나지 않아 10초를 채우고 강제 종료된다"였습니다. 그런데 앱 이미지는 Node 24이고, [Node 문서](https://nodejs.org/docs/latest-v24.x/api/http.html#serverclosecallback)에 따르면 v19부터 `server.close()`는 "요청을 보내거나 응답을 기다리는 중이 아닌 연결"(쉬는 연결)을 바로 닫습니다. 그래서 처음 의심은 옛 Node 기준입니다.
  - 남는 의심: 종료 신호 순간 **처리 중이던** 연결은 닫지 않고, 그 연결이 응답을 마치고 쉬게 된 뒤 어떻게 되는지는 문서에 없습니다. 쉬는 연결을 닫는 기본 시간(`keepAliveTimeout`)은 5초입니다. 처리 중이던 연결이 5초 동안 열려 있으면 종료가 그만큼 늦어집니다. [net 문서](https://nodejs.org/docs/latest-v24.x/api/net.html#serverclosecallback)대로 `close` 콜백은 모든 연결이 끝나야 불립니다.
- 로컬 한계 (실행 전에 적어 둠):
  - 로컬에는 ALB가 없습니다. 그래서 종료 신호 뒤 새로 보낸 요청은 다른 서버로 가지 못하고 연결 거부를 받고, 서버가 1대라 새 버전이 뜰 때까지 예약을 받을 곳이 없습니다(다운타임). 실제 배포는 ECS 롤링 배포([ADR-010](../04-decisions.md#adr-010))입니다. 새 태스크가 먼저 뜨고, ALB가 옛 태스크로 새 요청을 보내지 않게 한 뒤(대상 등록 해제, draining) 종료 신호를 보내므로 사용자에게 다운타임이 없어야 합니다 → 4단계. 그래서 "끊긴 요청 0"은 종료 신호 순간 처리 중이던 요청 기준으로 정하고, 예약 못 받는 시간은 측정만 합니다.
  - [ALB 문서](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html)의 대상 등록 해제 대기(deregistration delay) 기본값은 300초입니다. 그대로 두면 태스크 하나를 바꿀 때마다 최대 5분을 기다립니다 → 2단계 설계 때 정합니다.
  - k6는 VU를 돌아가며 쓰므로(초당 10건, VU 200개) 한 VU가 연결을 다시 쓰는 간격이 쉬는 연결 5초보다 깁니다. 실제 ALB는 앱과의 연결을 여러 사용자 요청에 계속 다시 씁니다(등록 해제 뒤에는 새 요청을 보내지 않음).
  - k6(Go)는 `Idempotency-Key` 헤더가 붙은 요청이 재사용하던 연결에서 끊기면 스스로 한 번 다시 보냅니다(E-05와 같음). 그래서 옛 연결에서 끊긴 요청이 연결 거부로 보일 수 있습니다. 처리 중이던 예약은 메시지가 아니라 받은 상태로 판정하므로 이 기준에는 영향이 없습니다.
  - 새 버전이 뜬 직후 k6의 DNS 대기(E-05 로컬 한계)는 기준에서 빼고 측정만 합니다.
  - DB 2초 멈춤, 1초 간격 다시 누르기, 최대 20번은 임의로 정한 값입니다. k6·앱·DB가 같은 PC입니다(E-05와 같음).
- 고칠 때: 회귀 테스트는 시간(sleep)이 아니라 상태로 맞춥니다(E-04와 같음).
- 실행 전 예측 (2026-11-05, 사용자):
  1. 종료 신호 → 앱 종료: 10초여도 괜찮다. AWS에서는 새 버전으로 넘어가면서 ALB가 알아서 넘겨 준다.
  2. 정상 종료 여부: 어차피 문 닫아서 없어질 서버라 강제 종료하지 않아도 되지 않을까.
  3. 처리 중이던 예약 약 10건: 1건만 예약 완료, 나머지는 끊김.
  4. 예약 못 받는 시간: 10초.
  5. 다시 누르기로 늘어난 요청: 예측 없음.
  6. 다시 누른 사람이 답을 받기까지: 길어도 3초.
  7. 중복·유실: 없어야 한다.

  - 종료가 7.3초 걸린 이유: 처리 중이던 예약은 DB를 푼 직후(종료 신호 1초 뒤) 모두 답을 받았습니다. 남은 6.2~6.3초는 할 일 없이 쉬는 연결이 닫히기를 기다린 시간입니다. 같은 Node(v24.22.2)로 따로 재현했습니다. 요청 처리 중에 `server.close()`를 부르면 응답은 `Connection: keep-alive`로 나가고, 그 연결은 쉬는 연결 대기 `keepAliveTimeout` 5초 + 여유 `keepAliveTimeoutBuffer` 1초 = 6초 동안 열려 있다가 닫힙니다. 그다음에야 `close` 콜백이 불렸습니다(응답 528ms → 콜백 6528ms). 처음 의심("끝나지 않아 강제 종료")이 아니라 '남는 의심'이 맞았습니다.
  - 영향: 강제 종료까지 남은 여유가 2.7초입니다. 종료 신호 뒤 3.7초 넘게 걸리는 요청이 있으면 10초를 넘겨 강제 종료되고, 그 순간 처리 중이던 요청이 끊깁니다(ECS 기본 30초면 여유 23.7초). 로컬(서버 1대)에서는 이 6초만큼 예약 못 받는 시간도 늘었습니다. AWS 롤링 배포에서는 ALB가 먼저 새 요청을 끊고(등록 해제) 처리 중 요청이 끝난 뒤 종료 신호가 가므로, 그때의 쉬는 연결은 `close()`가 바로 닫아 사용자 영향은 없을 것으로 봅니다 → 4단계에서 확인.
  - 개선 후보 (이번에 고치지 않음): 종료 신호 뒤 응답을 마친 연결을 바로 닫으면(예: 응답이 끝날 때 `server.closeIdleConnections()` 부르기) 6초를 줄일 수 있습니다. 기준은 통과했고 AWS에서는 사용자 영향이 없어 후속 후보로 둡니다.
  - 다시 누르기로 요청이 68% 늘어난 이유: 서버 1대라 8초 넘게 받을 곳이 없어 1초마다 최대 9번 다시 눌렀습니다. 화면에 자동 재시도를 넣는다면 횟수 제한과 점점 늘어나는 간격(지수 백오프)이 필요한 이유입니다. 롤링 배포에서는 0이어야 합니다 → 4단계.
  - 첫 시도 실패가 E-05(약 13%)보다 많은 이유: 예약 못 받는 시간이 더 길었습니다(E-05는 강제 종료 뒤 정해 둔 5초 + 시작 시간). 두 실험의 중단 시간은 스크립트가 정한 값이 달라 그대로 비교하지 않습니다.
- 예측과 비교 (사용자 예측):
  1. 10초여도 괜찮다 → 7.3초로 10초 안이었습니다. 다만 그중 6.3초는 쉬는 연결을 기다린 시간이라, 느린 요청이 남아 있으면 10초를 넘길 수 있습니다. "AWS에서는 ALB가 넘겨 준다"는 새 요청에는 맞고, 처리 중이던 요청은 옛 서버가 마저 끝내야 합니다(이 실험이 확인한 것).
