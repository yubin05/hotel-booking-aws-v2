# 5단계 리전 복원 드릴 — 실행 절차와 측정 결과 정리 현황

서울 리전 장애를 선언하고, 도쿄에서 **복제된 백업으로 DB를 살려** 손님을 받은 뒤 서울로 되돌리는 훈련입니다. **실험 실행 완료는 2026-11-21 사용자 확인**, 단 이 문서에는 정식 RTO·RPO 수치 및 4·5단계 실패율 교정 결과가 아직 기록되지 않았습니다. **측정·검증되지 않은 시간을 임의로 완료 수치로 쓰지 않습니다.** 실측 RTO · RPO를 잠정 목표(리전 RTO 1시간, [ADR-036](../04-decisions.md#adr-036))와 비교한다. 흐름은 [02 8 · 9절](../02-architecture.md#8-리전-장애-복구-흐름-backup--restore), 결정은 [ADR-062](../04-decisions.md#adr-062), 실행은 [런북 5-8](../../infra/README.md#5-8-리전-복원-드릴-5단계), 스크립트는 [drill/region.sh](../../drill/region.sh).

## 단계 (스크립트가 시각을 남김)

| 단계 | 하는 일 | 누가 |
|---|---|---|
| 0 사전 | 서울 apply `-var backup_replication=true`로 백업이 도쿄로 복제되는 중. 손님 역할(writer) 시작 → 도쿄의 복원 가능 시각이 손님 가입 + 1분을 넘을 때까지 기다림 | 사용자 apply, 스크립트 |
| ② 장애 선언 | 이 순간 도쿄의 **가장 최근 복원 가능 시각**을 기록하고 서울 앱을 0으로(멈춤 흉내) | 스크립트 |
| ③ 도쿄 복원 | `infra/tokyo` plan → 사람 확인 → apply: 인프라 + 그 시각으로 RDS 시점 복원(한 번에) | 스크립트, 확인은 사용자 |
| ④ 데이터 확인 | 도쿄 안 sql 태스크: 손님 쓰기 몇 번까지 들어 있나, 주요 표 행 수 | 스크립트 |
| ⑤ 전환 | `infra/global -var active_region=ap-northeast-1` plan → 확인 → apply (CloudFront 원본만 바꿈, DNS 그대로) | 스크립트, 확인은 사용자 |
| ⑥ 복구 끝 | 손님 쓰기가 도쿄 앱에서 성공한 시각 | 스크립트 |
| 되돌리기 ① | 도쿄 앱 0(계획된 점검, 쓰기 멈춤) | 스크립트 |
| ② 대조 | 서울 옛 DB에서 도쿄로 못 간 쓰기를 덮기 전에 뽑아 둠(= 잃은 데이터 목록) | 스크립트 |
| ③ 덤프 이관 | 도쿄 dump 태스크(덤프 · 잠금 · 미리 서명 PUT) → 서울 이관 버킷 → 서울 restore 태스크 → 체크섬 비교 | 스크립트 |
| ④ ~ ⑥ | 서울 앱 2 ~ 4 → global 서울로 → 손님 쓰기가 서울에서 성공 | 스크립트, 확인은 사용자 |
| 정리 | 도쿄 destroy, 드릴을 다 마치면 서울 복제 끄기 + `region.sh cleanup` | 사용자 |

- **장애 흉내 방식:** 서울 앱 태스크를 0으로(오토스케일링 범위도 0). 실제 리전 장애는 서울 API까지 안 될 수 있지만 그건 재현하지 않는다(한계). CloudFront · Route 53 · Terraform state(도쿄 버킷)는 서울 장애와 무관한 곳에 있다(ADR-012 · ADR-025)
- **복원 시점을 장애 선언 때로 고정하는 이유:** 드릴에서는 서울 DB가 살아 있어 복제가 계속 따라온다. 그대로 "가장 최근"으로 복원하면 실제 장애보다 데이터를 덜 잃는 것처럼 보인다. 선언 순간 값으로 고정해야 실제와 같은 RPO가 나온다

## 재는 것

| 지표 | 뜻 | 계산 |
|---|---|---|
| RTO | 장애 선언부터 손님 쓰기가 도쿄에서 성공할 때까지 | marks.log `rto_end − t0`. **사람 확인(plan 보고 yes) 시간은 따로 적고 뺀 값도** |
| 단계별 시간 | 02 9절 RTO 식(판단 + 인프라 + DB 복원 + 앱 기동 + 검증 + CloudFront) | `tokyo_apply → tokyo_done`(인프라 + DB), `check`, `global_to_tokyo_*`, 마지막 → `rto_end`(앱 기동 · 반영) |
| RPO | 장애 선언 − 복원된 데이터의 마지막 쓰기 시각 (02 9절) | writer.log의 성공한 쓰기 중 도쿄에 남은 가장 큰 순번의 시각. 같이: 잃은 쓰기 건수, 예상값(선언 − 복원 가능 시각) |
| 대조 | 서울 옛 DB에서 복원 시점 뒤 바뀐 예약(새 예약 · 날짜 변경 · 취소)을 덮기 전에 뽑음 = 고객사가 처리할 목록 | lost-in-seoul.txt에서 `drill_lost = 1`인 행 수 = 보고서의 잃은 쓰기 건수. 예약은 취소해도 행을 지우지 않고(status) `updated_at`이 바뀌어 잡힌다(앱 스키마에 대조용 색인). **한계:** 예약 표만 본다. 다른 표(회원 · 쿠폰 등)와 행을 실제로 지우는 변경은 MySQL binlog 비교가 필요(하지 않은 것) |
| 되돌리기 중단 | 도쿄 멈춤부터 서울에서 쓰기 성공까지 | `failback_end − failback_start` |
| 데이터 일치 | 되돌린 서울 = 도쿄 | 12개 표 체크섬(3단계 이관과 같은 checksum.sh) |
| 멱등성 | 끊긴 사이 다시 보낸 예약이 둘로 늘지 않음 | 같은 순번에 예약 번호 하나 |

## 실험 설계 점검표

| 점검 | 어떻게 |
|---|---|
| 1. 응답 시간 = 손님이 기다린 시간 | writer가 연결 포함으로 잼. 이 드릴의 주 지표는 시각(RTO · RPO) |
| 2. 기대 결과 · 숨은 기준을 미리 | 아래 예측. 체크섬 불일치 · 중복 예약 · 대조 건수 불일치는 실패 |
| 3. 같은 조건 3회 | 3회. 회차마다 도쿄 destroy 뒤 다시 run (서울 복제는 켠 채) |
| 4. 손 조작은 스크립트로 | 장애 선언 · 복원 시점 · 확인 SQL · 덤프 이관을 스크립트가. Terraform 확인(yes)은 사람이라 시간을 따로 셈 |
| 5. 환경 한계 | 서울 API는 살아 있음(장애 흉내), 손님 PC 한 대, 부하 없음(초당 5건) |
| 6. 분석 스크립트를 미리 | drill-report.mjs(RPO · 끊김 · 중복) 자체 점검 통과, 가짜 서버로 writer 확인 |
| 7. 회귀 테스트 | 해당 없음 |
| 8. 스모크 | 가짜 서버 확인(Claude, 기록 안 함). AWS 첫 apply에서 확인할 가설 2개(아래) |

**첫 apply에서 확인할 가설 (문서로 확정 못 함)**
- 받는 쪽 암호화 키로 도쿄의 AWS 관리 키(`aws/rds`)를 쓸 수 있는지: 문서에 없음. 거부되면 도쿄에 고객 관리 키를 만든다
- 암호화된 백업 복제에 미리 서명한 주소(PreSignedUrl)가 필요한지: API 문서는 "GovCloud에서만 쓰고 다른 리전에선 무시", 사용 설명서는 "암호화하면 필요"로 엇갈림. Terraform 예시는 없이 씀 → 없이 시도
- 복제 보관 기간 1일이 허용되는지

## 예측 (실행 전)

근거: RDS는 변경 로그를 **5분마다** S3에 올린다([RDS 시점 복원 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)). 도쿄 인프라 apply는 11-15 전환 PoC에서 9분 남짓(DB는 빈 DB). 시점 복원 · 복제 지연 시간은 문서에 숫자가 없어 가설.

| 예측 | 뜻 | Claude (가설) | 사용자 |
|---|---|---|---|
| RPO | 장애 때 잃는 데이터의 시간 폭 | 5 ~ 10분 (5분 로그 주기 + 복제 지연) → 잃은 쓰기 300 ~ 600건(초당 1건) | 실행 전에 받음 |
| 도쿄 apply | 인프라 + DB 시점 복원 + 비밀번호 금고 붙이기 | 20 ~ 35분 | |
| RTO (사람 확인 뺀 값) | 장애 선언 → 도쿄에서 쓰기 성공 | 25 ~ 45분, 목표 1시간 안 | |
| 되돌리기 중단 | 도쿄 멈춤 → 서울에서 쓰기 성공 | 8 ~ 15분 (덤프 이관 2분대 + 서울 앱 · 전환) | |
| 체크섬 · 대조 · 중복 | | 일치 · 일치 · 0 | |

- RTO가 1시간을 넘으면 가장 느린 단계를 Pilot Light(도쿄 DB 복제본)로 바꾸는 것을 검토한다(02 9절)
