|---|---|

## 기록

- 측정: 에러율 1%를 넘는 지점의 처리량(초당 요청 수), p95 응답 시간.
- 의심: 앱의 DB 연결이 10개뿐이고([db.ts](https://github.com/yubin05/hotel-booking-aws-v2/blob/d04aad9257eb038e2eb3446131102b9de7aadf5e/app/src/db.ts)) 대기 줄에 제한이 없습니다. 그래서 몰려도 에러 대신 응답 시간만 늘어날 수 있습니다. 에러율만으로는 한계를 못 잡을 수 있으니 p95 기준(예: 1초)도 함께 봅니다.
- 로컬 숫자는 PC 성능에 좌우되므로 AWS 숫자와 직접 비교하지 않습니다. 로컬에서는 무엇이 먼저 느려지는지와 데이터가 깨지지 않는지를 봅니다.
- 시나리오: 방문 하나를 화면 흐름대로 보냄(화면 하나가 동시에 부르는 API는 `http.batch`로 한꺼번에). 방문의 10%는 로그인, 3%는 예약(1~90일 뒤, 1~3박), 5%는 내 예약 확인. 화면 사이 5~20초. 요청 종류별 p95 합격 기준 추가. 데이터는 [seed-volume.sql](../../scripts/seed-volume.sql)로 숙소 1,000 / 객실 5,000 / 회원 2만 / 지난 예약 10만 / 리뷰 5만. 방문 하나가 약 1분이라 끝(예약)까지 가는 사람이 나오도록 500명을 90초 유지
- 측정하지 않는 것: 숙소 이미지와 웹 화면 파일(HTML·JS·CSS). 이미지는 외부(Unsplash) URL이라 브라우저가 우리 서버를 거치지 않고 직접 받고, 남의 서버에 부하를 거는 것도 안 됩니다. 웹 화면 파일은 AWS에서 CloudFront가 캐시해 앱까지 오지 않습니다. 이미지까지 포함한 "화면이 뜨는 체감 속도"는 부하와 별개로 브라우저 1대로 잽니다(Lighthouse)
- 실행 전 예측 (2026-11-05): ① 서버 에러 0건 ② 화면 하나가 API 2~3개를 부르므로 초당 요청이 많아짐 ③ 가장 느린 요청은 예약(DB에 쓰기 때문) ④ 추천 숙소(홈 첫 화면)는 사용자가 지연을 못 느낄 만큼, 0.1초 이하 ⑤ 로그인 p95는 길어도 1초 ⑥ 예약 수는 예측 없음 (계산상 방문 약 1,000번 × 3% ≈ 25~30건) ⑦ 요청 종류별 p95 기준을 모두 지킴 (지켜야 평소라고 할 수 있음)
- 1차 실행 (2026-11-05 11:21, `e01-normal-traffic-20261105-112142`): 합격 기준 모두 통과. 서버 에러 0 (요청 11,761건이 모두 200·201), 응답 확인 10,404건 100% 통과. 500명 유지 구간(30~120초)은 초당 86.6건. 유지 구간 p95는 로그인 180ms > 추천 숙소 26ms > 검색 21ms > 예약 19ms > 나머지(숙소·리뷰·도시·쿠폰·내 예약) 4~6ms. 10초 구간별 전체 p95는 사용자 50명대(0~10초) 23ms, 500명 유지 내내 17~22ms로 사람 수가 늘어도 그대로. 방문 1,085번, 예약 28건(409 0건). 방문 210번은 끝날 때 사용자 수를 줄이며 중간에 멈춤(실패 아님). 정합성 검사 모두 0, k6 예약 28건 = DB 28건. 그래프·표: `node scripts/e01-report.mjs <실행>.json.gz`
- 예측과 비교: ① 맞음 ② 초당 약 87건. 화면당 API는 평균 2.2개지만 화면 사이에 평균 12.5초를 쉬므로 500명 × 2.2개 ÷ 12.5초 ≈ 88건 ③ 가장 느린 건 예약이 아니라 로그인(비밀번호 해시를 일부러 느리게 계산). 그다음이 숙소 1,000개를 훑는 추천 숙소·검색이고, 예약은 객실·날짜 몇 줄만 읽고 써서 빠름. 느린 원인은 "쓰기"가 아니라 "한 번에 훑는 데이터 양" ④ 26ms로 0.1초 안 ⑤ 180ms로 1초 안 ⑥ 28건 (계산 25~30건) ⑦ 모두 통과
