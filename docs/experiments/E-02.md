## 기록

- 0단계 테스트는 동시 10건이었고, 여기서는 수를 늘리고 날짜가 엇갈리는 예약(1~3일, 2~4일 …)을 섞습니다.
- 스크립트: [e02-popular-room.js](../../load/e02-popular-room.js). 시드 첫 숙소의 스탠다드 룸 하나에 200명(계정 200개)이 같은 순간 한 번씩 예약합니다. 100명은 모두 60일 뒤 2박이고, 나머지 100명은 70일 뒤부터 하루씩 밀린 2박 10가지(10명씩)라 이웃 날짜끼리 하루씩 겹칩니다. 엇갈린 쪽 성공 수는 도착 순서에 따라 4~5건입니다. 2차(2026-11-05)부터는 같은 구간의 밤 11개마다 1박을 10건씩 더해 310명이고, 끝나면 그 구간에 빈 밤이 없어야 합니다.
- 측정: 응답 코드 분포, 교착 발생 수. `SHOW ENGINE INNODB STATUS`는 마지막 교착 1건만 보여 주므로 개수는 `SELECT COUNT FROM information_schema.INNODB_METRICS WHERE NAME='lock_deadlocks'`로 셉니다(MySQL 8.4에서 기본으로 켜져 있고, DB를 새로 띄우면 0부터 셈).
- 의심: MySQL에서 같은 키를 기다리던 INSERT들은 앞 트랜잭션이 취소되면 서로 교착할 수 있습니다. 그러면 409 대신 500이 나갑니다.
- 실행 전 예측 (2026-11-04): 같은 날짜는 1건만 성공하고 99건은 거절, 엇갈린 날짜는 날짜마다 예약이 0건 또는 1건, 겹치는 요청은 모두 409, 500 0건, 교착은 0건일 것 같지만 생길 수도 있음(확신 없음).
- 1차 실행 (2026-11-04 17:38): 201 5건(같은 날짜 1건, 엇갈린 날짜 4건), 정상 거절 409 195건, 예상 밖 응답 0건(500 0). 200건이 0.3초 안에 모두 끝남(예약 한 건 최대 0.28초). 교착 0건(`lock_deadlocks` 0). 정합성 검사 모두 0, k6 예약 5건 = DB 5건. 엇갈린 쪽 확정 예약은 1/13~15, 1/16~18, 1/19~21, 1/22~24이고, 남은 빈 밤(15·18·21일)은 모두 하룻밤씩 떨어져 있어 2박 요청이 들어갈 자리가 없음 (거절 195건이 모두 정당)
- 예측과 비교: 모두 예측대로. 다만 교착은 앞 예약이 취소되는 순간 그 날짜를 기다리던 요청이 둘 이상 있어야 생기는 타이밍 문제입니다. 이번 1회 실행에서 0건이었다고 일어날 수 없다는 증명은 아닙니다. 지금 코드에서는 교착이 나면 500으로 나갑니다
- 검토 (2026-11-05): 이중 예약·유실은 확인했지만 교착 의심은 약하게만 확인했습니다. ① 취소·날짜 변경을 섞지 않음: MySQL 문서의 INSERT 잠금 예시에는 "앞 트랜잭션 롤백" 말고 "그 행을 지우고(DELETE) 확정(커밋)하는 순간 기다리던 INSERT 둘이 교착"도 있는데, 앱의 예약 취소·날짜 변경이 바로 이 동작입니다(실사용: 인기 객실 취소표가 풀리는 순간 여러 명이 누름). ② 잠금을 실제로 기다린 횟수(`Innodb_row_lock_waits`)를 보지 않아 교착 0이 "많이 부딪혔는데도 0"인지 "덜 부딪혀서 0"인지 모름. ③ 1회 실행. ④ 앱의 DB 연결(커넥션 풀)이 10개라 DB 안에서 동시에 처리되는 예약은 최대 10건. AWS에서 태스크가 늘면 더 많아지므로 위 표의 AWS 칸을 고침
- 보강: 확률에 맡겨 k6를 여러 번 돌리는 대신, 취소 순간을 순서대로 만드는 테스트로 확인합니다([booking.test.ts](https://github.com/yubin05/hotel-booking-aws-v2/blob/d04aad9257eb038e2eb3446131102b9de7aadf5e/app/test/booking.test.ts)의 "취소가 확정되는 순간 …"). 취소 쿼리를 열어 둔 채 같은 날짜 예약 2건이 잠금을 기다리게 한 뒤 확정합니다. 기대: 1건 201, 1건 409
- 보강 테스트 실행 전 예측 (2026-11-05): 남은 자리가 1개라면 성공 1명, 나머지는 모두 "이미 예약됨"(이 테스트는 2명이라 409 1건), 서버 오류 0명 → 테스트 통과
- 보강 테스트 결과 (2026-11-05): 통과(전체 테스트 26개 모두 통과). 두 예약이 취소의 잠금 앞에서 실제로 기다리는 것을 DB의 실행 중 쿼리 목록(`SHOW FULL PROCESSLIST`)으로 확인한 뒤 취소를 확정(커밋)했고, 1건 201·1건 409·500 0건. 예측대로입니다. MySQL 문서 예시와 달리 MySQL 8.4에서는 이 순서로 교착이 생기지 않았고, 왜 다른지는 확인하지 못했습니다. 테스트는 회귀 테스트로 CI에 남겨 push마다 확인합니다. 테스트가 k6보다 가혹한 조건(취소를 일부러 멈춰 둠)이라 k6 취소표 실험은 따로 하지 않습니다
- 빈 밤 확인 (2026-11-05): 1차 실행에서 남은 15·18·21일 밤은 1박이면 예약돼야 합니다(퇴실하는 날 = 다음 손님이 들어오는 날). 이 경계를 확인하는 테스트가 없어 추가했습니다([booking.test.ts](https://github.com/yubin05/hotel-booking-aws-v2/blob/d04aad9257eb038e2eb3446131102b9de7aadf5e/app/test/booking.test.ts)의 "두 예약 사이에 남은 하룻밤 …"). 예측: 1박 201, 하룻밤이 겹치는 2박 409. 결과: 통과(전체 테스트 27개 모두 통과). 예측대로 1박 201, 2박 409. 빈 밤은 버그가 아니라 1박 요청이 없었을 뿐입니다
- 2차 실행 (2026-11-05 13:35, `e02-popular-room-20261105-133528`): 1박 요청을 밤마다 10건씩(110건) 더해 310명. 같은 날짜(1/4~6) 201 1건, 1월 14~25일 구간 예약 6건(14~16, 16~18, 18~20, 20~22, 22~24, 24~25)으로 빈 밤 0, 409 303건, 500 0건, 교착 0건(`lock_deadlocks` 0), 정합성 검사 모두 0, k6 예약 7건 = DB 7건. 0.4초 안에 모두 끝남
- 2차 예측과 비교: 실행 전 예측은 따로 받지 않았습니다. 계산상 기대(같은 날짜 1, 빈 밤 0, 구간 예약 6~11건, 500 0, 교착 0)와 모두 맞습니다. 구간 예약 6건은 가능한 최소로, 이번에는 2박이 먼저 처리돼 빈틈없이 이어졌고 남은 24일 밤만 1박이 채웠습니다
