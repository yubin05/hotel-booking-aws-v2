# 01. 시나리오와 요구사항

이 문서의 회사와 요구사항은 포트폴리오를 위해 **가정한 것**입니다. 가정은 v1 발표 자료의 시나리오를 따르되, v2에서 실제로 측정할 수 있는 형태로 고쳐 썼습니다.

## 고객: Sponge Trip

- 국내 숙소 예약 플랫폼을 운영하는 소규모 회사
- IDC에서 웹(nginx)–API–DB(MySQL) 3계층 단일 구조로 운영
- 이미 사용자와 예약 데이터가 있는 **운영 중인 서비스**

## 사건

구독자 150만 명의 여행 유튜버가 서비스를 소개한 영상이 24시간 만에 조회수 800만을 넘기면서 트래픽이 급증했습니다(일일 사용자 약 40배). 서버 과부하로 예약 서비스 전체가 약 4시간 중단됐고, 회사는 MSP인 우리에게 AWS 이관을 의뢰했습니다.

> 이 수치는 사건의 배경입니다. v2에서는 같은 규모를 재현하지 않고, **축소한 부하로 "이전 환경 대비 개선"과 "오토스케일링 동작"을 검증**합니다.

### 이관 후 대비할 급증 시나리오

| 시나리오 | 특징 | 대응 | 검증 |
|---|---|---|---|
| 바이럴 급증 (위 사건) | 예고 없이 몰림 | 목표 추적 오토스케일링 + CDN 캐시 | 부하에 따라 태스크가 늘어나는지, 에러율 |
| 선착순 쿠폰 이벤트 | 오픈 시각을 미리 알고, 그 순간에 극단적으로 몰림 | 예약 스케일링으로 미리 확장 + 요청 제한 + DB 조건부 갱신 | 초과 발급 0건, 남은 수량이 있는데 거절 0건, 응답 시간 |
| 성수기 | 몇 주 동안 높은 부하 | 기본 용량(최소 태스크 수, DB 크기) 상향 | 장기 테스트 대신 용량 계획과 비용 계산 |

## 이전 환경 (IDC)

v1에서 IDC를 재현한 CloudFormation 템플릿(`3tier-seoul.yml`, v1 git 이력)을 기준으로 정리했습니다.

| 특징 | 문제 |
|---|---|
| 모든 서버가 AZ 1개에, 기능별로 1대씩 | 서버 하나가 죽으면 그 기능이 통째로 중단 |
| 로드밸런서·오토스케일링 없음 | 트래픽이 몰리면 그대로 다운 |
| DB 서버 1대, 이중화·백업 체계 없음 | 데이터 사고에 무방비 |
| 수동 배포 | 배포 실수와 느린 복구 |

v2의 1단계에서는 이 환경을 앱 구조에 맞게 줄여서(웹+앱 서버 1대, DB 서버 1대, DB 서버의 인터넷 출구용 NAT 인스턴스 1대) 재현하고 부하 기준선을 잽니다.

## 요구사항

| # | 요구사항 | 검증 방법 |
|---|---|---|
| R1 | 트래픽이 급증해도 서비스를 유지한다 | k6로 이전 환경과 같은 부하를 주고 에러율·응답 시간 비교, 오토스케일링 동작 확인 |
| R2 | 서버나 AZ 하나가 장애 나도 서비스가 계속된다 | 태스크 강제 종료, RDS 강제 장애 조치 후 복구 시간 실측 |
| R3 | 실수나 장애로부터 데이터를 복구할 수 있다 | 시점 복구, 다른 리전 백업으로 복원 후 RPO 실측 |
| R4 | 리전 장애에도 서비스를 복구할 수 있다 | 다른 리전 복원 드릴 3회로 RTO 실측 후 목표 확정 (4시간 중단이 문제였으므로 그보다 확실히 짧아야 함) |
| R5 | 예약 데이터가 정확하다 | 같은 객실·날짜 동시 예약 시 1건만 성공, 같은 요청 반복 시 1건만 생성 |
| R6 | 트래픽이 폭증해도 비용을 예측할 수 있다 | 오토스케일링 상한, CDN 캐시, 요청 제한, 예산 알림 설정 확인 |
| R7 | DB와 백엔드는 인터넷에 노출하지 않는다 | 보안 그룹·서브넷 구성 확인, 외부 직접 접근 시도 |
| R8 | 바뀐 운영 방식(컨테이너)에 맞게 배포를 자동화한다 | 커밋부터 반영까지 시간, 실패 배포 자동 롤백 실측 |
| R9 | 선착순 쿠폰은 수량만큼만, 한 사람에 한 장씩 발급한다 | 동시 발급 테스트와 오픈 시각 부하 테스트(k6)로 발급 수·거절 수 확인 |
| R10 | 이용을 마친 예약에만 리뷰를 쓰고, 숙소 평점은 실제 리뷰와 일치한다 | 리뷰 동시 저장 테스트로 평점 집계 확인 |

## 가정과 제약

| 가정 | 설계에 미친 영향 |
|---|---|
| 기존 사용자·데이터·MySQL 백엔드가 있다 | 재개발이 아닌 이관 → AWS ([ADR-002](04-decisions.md#adr-002)) |
| 벤더 종속 탈피나 규제 요구는 없다 | 멀티클라우드 불필요 ([ADR-001](04-decisions.md#adr-001)) |
| 사내 인프라 담당자는 1명이다 | 쿠버네티스 운영 부담 불가 → ECS Fargate ([ADR-003](04-decisions.md#adr-003)) |
| 이관 시 새벽 점검 시간을 쓸 수 있다 | DMS 대신 덤프 이관 ([ADR-008](04-decisions.md#adr-008)) |
| 리전 장애 시 수 시간 내 복구면 받아들일 수 있다 | Backup & Restore 전략 ([ADR-009](04-decisions.md#adr-009)) |
| 평소 동시 접속은 약 500명이다 (사건 때 동시 접속 2만 ÷ 일일 사용자 40배. 1인 10분 이용, 하루 12시간 중 피크 2배로 보면 하루 사용자 약 2만 명) | 부하 테스트의 평소 규모 ([07 E-01](07-experiments.md)), AWS 최소 태스크 수와 비용 추정의 기준 |
| 개인정보를 다루며 서울 리전을 주 리전으로 쓴다 | 리전 간 백업은 국외(도쿄) 보관이 되므로, 실제 서비스라면 개인정보 국외 이전 요건을 검토해 고지해야 한다 |

## 범위

**포함**
- 회원가입·로그인 (앱 자체 JWT)
- 호텔·객실 조회
- 예약 생성·변경·취소·조회
- 쿠폰: 정액 할인, 선착순 수량, 1인 1매, 예약할 때 적용, 예약을 취소하면 반환
- 리뷰: 체크아웃한 예약에 1회, 숙소 평점·리뷰 수에 반영
- 헬스체크 엔드포인트

**제외** (v1에서 일부 구현 경험 있음)
- 찜(위시리스트), 문의, 공지
- 정률(%) 쿠폰, 리뷰 사진
- 이미지 업로드·리사이징, 추천, 번역
- 알림, 결제
- 실제 사건 규모(동시 접속 2만)의 부하 재현
