# 11. 계정 보안 점검 보고서 (2026-11-17)

2단계 인프라를 모두 올린 상태에서 AWS 계정과 인프라 설정을 표준 기준으로 점검했습니다. 발견한 항목을 **조치(고친 취약점) · 개선 계획 · 위험 수용(예외)**으로 나누고, 각각 근거를 남겼습니다. 앱 코드 쪽 점검은 [10 보안 점검](10-security.md)에 있습니다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 목적 | 직접 만든 인프라(서울 45 · global 13)와 계정 기본 설정에서 빠뜨린 보안 설정을 찾아 고치고, 고치지 않는 것은 이유를 남긴다 |
| 범위 | 서울(ap-northeast-2) 전체, 버지니아 북부(us-east-1: CloudFront · WAF · 인증서). 도쿄는 평소 복제 버킷 · ECR만 있어 제외(5단계에서 포함) |
| 기준 | AWS Foundational Security Best Practices(FSBP) v1.0.0 |
| 도구 | Security Hub CSPM(설정 점검), AWS Config(자원 상태 기록), GuardDuty(위협 탐지), CloudTrail(API 호출 기록). 구성 이유는 [ADR-057](04-decisions.md#adr-057) |
| 일시 | 2026-11-17 11:11 점검 켬 → 12:05 1차 결과 → 조치 후 재점검 → 11-18 아침 주기 점검 결과 반영 |
| 점검 시 상태 | 서울 · global · 앱(CD) 모두 올린 상태, 시드 데이터 |

## 2. 요약

**1차 결과(12:05):** 서울은 실패 53 · 통과 59, us-east-1은 실패 39 · 통과 23이었습니다. 계정 단위 항목은 두 리전에서 모두 세어지므로, 실패한 **고유 점검 항목은 59개**입니다. GuardDuty 위협 탐지는 0건이었습니다.

| 분류 | 고유 항목 | 처리 |
|---|---|---|
| [조치](#3-조치한-취약점) | 13 | 고침. CRITICAL 2개(전 세계에 열린 기본 보안 그룹, SSM 문서 공개 공유)를 포함 |
| [개선 계획](#4-개선-계획) | 3 | 앱 컨테이너 강화 · 비밀 자동 교체. 시험이 필요해 따로 진행 |
| [위험 수용](#5-위험-수용-예외) | 42 | 비용 · 설계 결정과 충돌. 이유 · 보완 통제 · 다시 볼 때를 기록 |
| [사용자 조치](#6-사용자-조치) | 1 | 보안 연락처 등록(개인정보라 코드 밖) |

**가장 큰 발견:** CRITICAL 1위는 우리가 만든 인프라가 아니라 **아무도 안 쓰던 서울 기본 VPC의 기본 보안 그룹**이었습니다. SSH(22) · MySQL(3306) · Kubernetes API(6443) 등 15개 규칙이 전 세계(0.0.0.0/0)에 열려 있었고, 예전 실습의 흔적으로 보입니다. 평소 사용자 권한으로도 ECS 서비스를 만들 때 이 그룹을 고를 수 있어서, 실수 하나로 바로 노출될 수 있는 상태였습니다. 점검 도구가 Terraform 밖의 자원까지 계정 전체를 본다는 점이 드러난 사례입니다.

- 모두 **무료**이고 서비스에 영향이 없는 설정입니다. 고친 코드는 `infra/security/account.tf` · `logs.tf`, `infra/modules/regional`, `infra/global`에 있고, 줄마다 점검 ID를 주석으로 달았습니다.
- 계정 기본값(SSM · EBS)은 점검 범위 밖인 도쿄에도 같이 걸었습니다. 평소 권한이 닿는 리전이기 때문입니다.

## 5. 위험 수용 (예외)

| 분류 | 점검 | 받아들이는 이유 | 보완 통제 | 다시 볼 때 |
|---|---|---|---|---|
| 유료 탐지 서비스 | Inspector.1 ~ 4, Macie.1, GuardDuty.5 ~ 8 · 11 ~ 13 | 추가 비용. EC2 · EKS · Lambda가 없고, S3에는 숙소 사진뿐이라 개인정보가 없음(Macie) | GuardDuty 기본 탐지 + S3 · RDS 로그인 보호 켬([ADR-057](04-decisions.md#adr-057)) | 3.5단계, GuardDuty 체험이 끝나기 전 |
| 인터페이스 엔드포인트 | EC2.10, 55 ~ 58, 60 | 엔드포인트마다 시간 요금. NAT + S3 게이트웨이로 결정([ADR-034](04-decisions.md#adr-034)) | 앱 · DB는 비공개 서브넷, 외부로는 NAT로만 | 비용을 다시 볼 때 |
| 로그 · 모니터링 저장 | CloudTrail.5, ELB.5, CloudFront.5, S3.9, Route53.2, RDS.9, RDS.6, ECS.12, SSM.6, EC2.6 | 저장 · 수집 비용. 매일 지우는 환경 | CloudTrail(S3 90일), 앱 로그는 CloudWatch Logs, VPC 흐름 · DNS 기록은 GuardDuty가 독립 사본으로 분석 | 3.5단계(사건 대응에 필요한 것만 켬) |
| 고객 관리 암호화 키 | CloudTrail.2 | KMS 키 월 $1 + 호출 비용 | S3 기본 암호화, 버킷 공개 차단, 로그 무결성 검증 | 실서비스로 바꿀 때 |
| 매일 만들고 지우는 설계 | RDS.5, ELB.6, RDS.8, CloudFront.4 | Multi-AZ는 AZ 장애 시험 때만 켬(비용). 삭제 보호는 매일 destroy와 충돌. 원본 전환은 사람이 판단([ADR-012](04-decisions.md#adr-012)) | 설계상 실운영은 Multi-AZ · 삭제 보호를 켬([ADR-005](04-decisions.md#adr-005)), 백업 7일 | 4 · 5단계 |
| 내부 구간 HTTP | ELB.21, ELB.22 | ALB → 컨테이너는 VPC 안 사설 구간. 앱에 인증서를 넣으면 관리 부담 | 입구(CloudFront · ALB)는 HTTPS, 앱 보안 그룹은 ALB에서 오는 것만 | 실서비스로 바꿀 때 |
| 우리 구조와 충돌 | EC2.172 | VPC 공개 접근 차단을 켜면 NAT · 인터넷 게이트웨이 통신도 막힘 | 공개 서브넷에는 NAT만, ALB는 내부용(CloudFront VPC Origin) | — |
| 해당 없음 · 다른 통제로 대체 | CloudFront.17, CloudFront.1, RDS.10, RDS.25, RDS.23, IAM.6 | 공개 사이트라 서명 URL이 필요 없음. 사진 CDN 루트 요청은 OAC 권한상 403이라 목록이 보이지 않음. DB는 비공개 서브넷 · 앱 전용 계정이고 관리자 비밀번호는 RDS가 Secrets Manager로 관리. 루트 계정은 가상 MFA가 켜져 있고 하드웨어 키가 없음 | 보안 그룹으로 DB 접근은 앱에서만, 루트 계정은 평소 쓰지 않음 | — |

## 8. 한계

- 1차 결과는 주로 "바뀔 때 도는 점검"입니다. 12 ~ 24시간마다 도는 주기 점검은 11-18 아침 결과로 보탭니다.
- 기준은 FSBP 하나입니다. CIS 같은 다른 기준은 넣지 않았습니다.
- 도쿄는 점검 범위 밖입니다. 계정 기본값만 같이 걸었습니다.
- 점검은 설정만 봅니다. 앱 코드의 취약점과 웹 공격 방어는 [10 보안 점검](10-security.md)에서 다룹니다.
