## 4. 원 요청문 (사용자가 붙여 준 것, 그대로)

> Claude, 호텔 예약 플랫폼 보안 포트폴리오 v3를 이어서 설계해줘. **대표 시나리오는 A(탈취된 회원 계정의 포인트 사용)이고, 보여주고 싶은 역량은 이상 거래를 탐지하고 추가 피해를 자동으로 막는 것**이야. B(호스트 계정의 고객정보 대량 열람)와 C(다계정 쿠폰 독식)는 후속 시나리오로 두고, 이번에는 A의 설계와 검증 기준부터 잡아줘.
>
> **현재 코드**
>
> - 앱 저장소는 [hotel-booking-app](https://github.com/yubin05/hotel-booking-app), 인프라 저장소는 [hotel-booking-aws-v2](https://github.com/yubin05/hotel-booking-aws-v2)야. 2026-11-23 조사 기준 `main`은 각각 `0ca94fc`, `25c2f97`이었어. 작업 전 현재 코드와 달라진 부분만 확인해줘.
> - 로그인 성공 로그 `login_succeeded`와 예약 생성 로그 `booking_created`는 `session_id`로 연결할 수 있어. 예약 로그에는 `points_used`가 있고, 포인트 원장에도 사용 세션이 남아. [인증 코드](https://github.com/yubin05/hotel-booking-app/blob/0ca94fc/src/auth/index.ts) · [예약 코드](https://github.com/yubin05/hotel-booking-app/blob/0ca94fc/src/booking/index.ts)
> - 관리자 복구 API는 이미 있어. `POST /api/admin/recover`에 세션 ID를 주면 그 세션이 사용한 포인트 중 아직 돌려주지 않은 금액을 복구하고, 관련 확정 예약을 취소해. 다만 이 작업으로 해당 JWT가 폐기되지는 않아. [포인트 원장](https://github.com/yubin05/hotel-booking-app/blob/0ca94fc/src/points/index.ts) · [관리자 복구 코드](https://github.com/yubin05/hotel-booking-app/blob/0ca94fc/src/admin/index.ts)
>
> **A에서 시연할 사건**
>
> 테스트 회원 한 명에게 평소 쓰는 세션과 탈취 상황을 가정한 시험 세션을 준비해. 시험 세션이 새로운 접속 환경에서 로그인한 직후 포인트를 사용해 예약하면, 로그인 기록과 사용 기록을 연결해 경보를 만드는 흐름이야. 새 IP만으로 차단하면 여행 중인 정상 회원도 걸리므로, 포인트 사용 시점·금액 같은 거래 신호를 함께 써줘. 탐지 임계값은 정상 거래와 비교해 조정할 가설로 제시해줘.
>
> **자동 대응의 범위는 의심 세션의 추가 포인트 사용을 보류하는 데까지**야. 같은 회원의 정상 세션은 계속 쓸 수 있어야 해. 운영자가 로그와 원장을 보고 부정 사용을 확인하면 기존 관리자 API로 첫 거래를 복구해. 첫 버전에서는 고객 포인트 환원이나 예약 취소를 자동화할 필요가 없어.
>
> **데모 완료 기준**
>
> 1. 정상 회원이 여행지에서 로그인하고 평소처럼 이용하는 대조 사례가 통과한다.
> 2. 시험 세션의 첫 포인트 사용이 경보로 이어지고, 운영자가 어느 세션이 어느 예약에 얼마를 썼는지 확인할 수 있다.
> 3. 보류가 적용된 뒤 같은 세션의 추가 포인트 사용은 거절되고, 그 요청으로 새 예약이나 원장 차감이 생기지 않는다. 같은 회원의 정상 세션은 영향을 받지 않는다.
> 4. 운영자가 복구하면 첫 거래의 포인트가 정확히 한 번 돌아오고 관련 확정 예약이 취소된다. 복구를 다시 시도해도 잔액이 늘어나지 않는다.
> 5. 첫 거래, 경보 생성, 보류 적용 시각을 따로 기록한다. 그사이에 통과한 거래가 있다면 건수와 금액도 결과에 포함한다.
>
> **후속 시나리오와 인프라 맥락**
>
> - **B**는 권한 있는 호스트가 자기 숙소 고객정보를 평소보다 많이 열람하는 상황이야. 기존 `host_bookings_viewed` 로그에 페이지와 반환 건수가 있어. 같은 페이지를 두 번 보면 건수도 두 번 잡히므로, 반환 행 수와 실제 영향 고객 수를 구분해줘. [호스트 코드](https://github.com/yubin05/hotel-booking-app/blob/0ca94fc/src/host/index.ts)
> - **C**는 실제 봇을 새로 만드는 작업까지 갈 필요 없어. 기존 k6 쿠폰 실험과 합성 테스트 데이터를 활용해 정상 고객과 다계정 집단의 발급 결과를 비교하면 돼. 지표는 초과 발급 여부와 함께 **정상 고객 발급 성공률, 다계정 집단 점유율, 정상 신규 회원 오탐률**을 봐줘. [기존 쿠폰 실험](https://github.com/yubin05/hotel-booking-aws-v2/blob/25c2f97/load/coupon-spike.js)
> - 리전 DR은 **Pilot Light**로 변경됐어. 도쿄의 RDS 읽기 복제본을 승격하고 앱 인프라를 올리는 리전 장애 대응이야. A의 포인트 피해는 세션 통제와 원장 복구로 처리해. [DR 드릴 기록](https://github.com/yubin05/hotel-booking-aws-v2/blob/25c2f97/docs/experiments/region-drill.md)
>
> **첫 답변에서는 A의 탐지 조건, 세션 보류를 검사할 코드 위치, 정상·이상 거래 검증 방법을 한 가지 최소 설계로 정리해줘.** 특히 현재 `booking_created`는 예약 트랜잭션이 끝난 뒤에 남으니, 첫 거래가 이미 완료된 시점과 후속 거래를 막을 수 있는 시점을 정확히 짚어줘.
